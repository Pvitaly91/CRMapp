# Checkbox Batch Printer

Локальна WPF-програма для Windows 10/11, яка завантажує **вже існуючі** фіскальні чеки через офіційний Checkbox API й пакетно друкує їх офіційні PNG-копії.

**Prom/Rozetka — необов’язковий додатковий модуль.** Для отримання, перегляду та друку достатньо налаштувати тільки Checkbox і принтер. Чек без замовлення — звичайний повноцінний чек.

Програма не створює, не фіскалізує і не змінює чеки або зміни. У коді відсутні виклики write-endpoint-ів Checkbox, окрім `cashier/signin`, потрібного для отримання JWT.

## Фоновий режим (1.0.7)

У «Налаштування → Фоновий режим» можна ввімкнути автоматичне оновлення (типово кожні 2 хвилини; 1/2/5/10), обрати робочий період чеків (типово 7 днів), залишення в треї, запуск із Windows та прихований старт. Після запуску програма спершу показує захищений локальний кеш, а потім читає Checkbox і ввімкнені Prom/Rozetka. Вкладка, видимість вікна та календар не керують циклом. Фон не друкує, не створює чеків/ТТН і не змінює замовлень.

Якщо ввімкнено «Залишати в треї», X приховує вікно. Подвійний клік на значку CRMapp його відкриває; меню значка має «Оновити зараз», паузу, налаштування й повний вихід. Звичайне завершення Windows не підмінюється приховуванням. Повторний запуск того самого Windows-користувача, каналу та кореня даних відкриває чинний екземпляр. Development і Production ізольовані. Автозапуск створюється **лише після вибору користувача** у власному HKCU Run-записі каналу та використовує фактичний EXE із `--background`; тестові збірки не реєструють його.

«Сповіщати Windows про нові замовлення» ввімкнено за замовчуванням. Після успішного фонового читання нові замовлення Prom/Rozetka об’єднуються в одне системне сповіщення з номерами замовлень; натискання відкриває CRMapp. Перший повний список нового магазину стає тихою базою, без повідомлень про давню історію. Захищений журнал `Marketplaces/order-notifications.dpapi` запобігає повторам після перезапуску. Вимкнені сповіщення не накопичуються. Windows може приховати повідомлення через власні налаштування сповіщень або «Не турбувати»; програма ці налаштування не змінює.

Список чеків зберігається в `receipts.dpapi` для облікового контексту касира: метадані, перевірений діапазон, час і відбитки; PNG у ньому немає. Замовлення, ручні рішення, автозв’язки й історія друку залишаються у своїх попередніх сховищах. Кешовані дані не позначаються як щойно перевірені. Зміна календаря поза завантаженим діапазоном запускає читання потрібних чеків, не змінюючи фонового робочого періоду. «Сьогодні» переходить на новий день за Києвом, але явно вибраний історичний діапазон не перемикається. Подробиці й межі перевірки: [BACKGROUND_SYNC_REPORT.md](docs/BACKGROUND_SYNC_REPORT.md).

## API

- Production host: `https://api.checkbox.ua`
- Авторизація: `POST /api/v1/cashier/signin`
- Пошук: `GET /api/v1/receipts/search`
- Зображення: `GET /api/v1/receipts/{receipt_id}/png`
- Офіційні джерела: [інтеграція](https://checkbox.ua/api-integration/), [Swagger](https://api.checkbox.ua/api/docs), [ReDoc](https://api.checkbox.ua/api/redoc)

Пошук завантажує тільки чеки поточного касира (`self_receipts=true`). Кілька вибраних чеків друкуються одним безперервним завданням із проміжком приблизно 2 мм і розділювальною рискою; це не додає службових сторінок між чеками. Над чеком із точним, ручним або ймовірним зв’язком друкується невеликий рядок «Замовлення №…». Чек без зв’язку друкується без цього рядка й додаткового відступу. Номер фіксується разом із підтвердженим набором чеків; офіційний PNG не змінюється. Успішно передані на друк рядки виділяються зеленим і мають статус «Надруковано». Деталі перевірки: [PRINT_ORDER_NUMBER_REPORT.md](docs/PRINT_ORDER_NUMBER_REPORT.md).

У «Налаштування → Checkbox» введіть логін та особистий пароль **касира** Checkbox. Вони можуть відрізнятися від даних входу до особистого кабінету. Поточна схема API визначає для `/api/v1/cashier/signin` саме ці два поля; ключ інтеграції для цього запиту не вимагається. Якщо сервер поверне HTTP 403, програма покаже відому причину (невірні дані касира, ключ доступу або деактивований касир), не записуючи пароль у журнал. Невдала перевірка не замінює збережений пароль.

## Дві незалежні вкладки

Поля «Дата від / Дата до» одразу фільтрують **і чеки, і замовлення** за календарною датою Києва. Для чеків поза завантаженим діапазоном програма запускає читання після зміни дат; старий фоновий діапазон не пересувається. Порожня дата знімає відповідну межу. Приховані рядки, галочки та архів не видаляються; усі завантажені конкуренти продовжують враховуватися в зіставленні.

Кнопка **«Оновити автоприв’язки»** оновлює замовлення та повторює зіставлення з урахуванням кешу, ручних рішень і фіскальних ключів. Вона доступна також після неповної перевірки. Деталі незмінених чеків повторно не завантажуються до завершення строку кешування; нові, змінені та відсутні в кеші деталі читаються за потреби. Якщо весь набір вхідних даних незмінний, використовується збережений результат. При зміні набору перевіряється весь граф кандидатів у пам’яті: старий ймовірний зв’язок не приховує нового конкурента. Збережений результат після перезапуску позначено в поясненні як кешований; нові зв’язки без повної перевірки API не створюються. Звіт: [AUTO_LINK_CACHE_REPORT.md](docs/AUTO_LINK_CACHE_REPORT.md).

Поруч із пошуком доступні **«Виділити всі»** (усі чеки поточного відфільтрованого списку), **«Зняти всі»** (включно з прихованими позначками активної вкладки) та **«Чеки за сьогодні»**. Остання кнопка встановлює сьогоднішній день за Києвом, скидає пошук/тип чека й одразу завантажує список. Календарна кнопка «Сьогодні» працює так само. Після успішного передавання одиночного чека або пакета на друк галочки переданих чеків знімаються у вкладці, з якої запущено друк. Приховані чеки та вибір іншої вкладки зберігаються; скасування або помилка не знімає галочки. Зелена позначка й історія друку залишаються.

Після запуску відкривається **«Усі чеки»**: усі доступні поточному касиру чеки за обраний період, незалежно від магазинів, прив’язок, стану API чи кешу маркетплейсів. Пошук тут використовує тільки дані самого чека. Доступні фільтр типу, сортування, галочка з першого кліку, офіційний PNG, пакетний друк та історія. F5 / «Оновити» завантажує лише Checkbox і не запускає синхронізацію замовлень. `self_receipts=true` і наявні права доступу не змінено.

**«Чеки та замовлення»** містить дві таблиці поруч: ліворуч **завантажені замовлення за спільним фільтром дат** увімкнених Prom/Rozetka-магазинів, включно з непов’язаними; праворуч — чеки Checkbox. Замовлення мають незалежні пошук/фільтр і показують точні, ручні та ймовірні зв’язки. Вертикальний розділювач між таблицями можна пересувати ліворуч/праворуч, змінюючи ширину панелей; кожна таблиця має власну прокрутку. Локальний кеш читається при запуску; за ввімкненого фону замовлення й зв’язки оновлюються незалежно від відкритої вкладки. F5 оновлює чеки; для явного оновлення замовлень є окрема кнопка або «Оновити зараз» у треї. Для самого списку замовлень успішний вхід у Checkbox або наявність чеків не потрібні. Це всі **завантажені/кешовані** замовлення, а не обіцянка отримати всю історію магазину одним запитом. Для вимкнення модуля зніміть «Увімкнути підключення»: секрети, кеш і ручні рішення залишаться збереженими.

Стан оновлення, пояснення точних/ймовірних зв’язків, кількість/область завантажених замовлень і обмеження поточного касира сховані під кнопкою **ⓘ** біля прапорця автоприв’язки. Наведіть на неї курсор, щоб прочитати актуальні повідомлення; постійного великого текстового блока над таблицями немає. Над таблицею замовлень лише один рядок: поле пошуку, фільтр, «Прив’язати вибрані» й «Оновити автоприв’язки». У дуже вузькій панелі цей рядок прокручується горизонтально, не переноситься й не приховує кнопки назавжди.

Кожна вкладка має окремі пошук, фільтри, сортування, поточний рядок і позначки друку. Період завантаження Checkbox, самі рядки/PNG та історія спільні; дубльованих серверних запитів чи сховищ для вкладок немає. «Вибрати всі видимі», «Зняти весь вибір», Ctrl+A, Ctrl+P і нижні кнопки діють на **активну** вкладку. Зняття всього вибору прибирає також її приховані позначки, але не змінює позначки іншої вкладки.

Друк бере лише позначені видимі чеки в порядку активної таблиці. Підтвердження показує точний список і кількість прихованих позначок, які не потрапили в пакет. Принтер, IDs та порядок фіксуються: перемикання вкладки чи завершення синхронізації не змінює пакет і не дозволяє паралельно запустити другий. Стан друку одразу спільний для обох таблиць, але галочки між ними не копіюються. Прив’язка до замовлення для друку не потрібна.

## Необов’язкові замовлення Prom.ua та Rozetka

Для однакової суми й дати додатково порівнюється **сумарна кількість товарних одиниць** у повних кошиках. Наприклад, два замовлення по 201 грн із 1 та 2 одиницями можна розрізнити за відповідними чеками. Це сума `Quantity`, не число рядків: один рядок ×2 та два рядки ×1 мають однакову кількість. Якщо цей критерій усунув конкурентів і пара стала взаємно унікальною, статус — «Автозв’язок: сума й кількість товарів» (або сильніший «сума й товари», якщо підтверджено також назви). Однакова кількість не доводить тотожність товарів. Невідомі, дробові, неповні або скориговані кількості не використовуються для виключення конкурента; ручні й фіскальні зв’язки зберігають пріоритет. Зміна версії алгоритму інвалідує старі результати автокешу, але зберігає придатні деталі чеків. [Звіт перевірки кількості](docs/QUANTITY_MATCHING_REPORT.md).

У «Налаштування → Маркетплейси» додайте магазин, увімкніть підключення і введіть секрети **тільки локально**:

- Prom — API-токен з мінімальним правом читання замовлень.
- Rozetka — логін і пароль продавця; програма отримує токен через документований `POST /sites`.

Натисніть «Перевірити підключення», потім «Зберегти». Перейдіть на «Чеки та замовлення» — оновлення почнеться автоматично. Для прив’язки додатково завантажте чеки Checkbox. За замовчуванням завантажується історія замовлень від 30 днів до початку періоду чеків; без завантажених чеків береться обраний календарний період. Кнопка «Розширити на 30 днів» збільшує завантажену історію, але автозіставлення за сумою працює тільки в межах дати чека. Фактичний діапазон, останнє успішне оновлення і неповний результат показуються у вкладці інтеграцій. Календар використовує час Києва. Для дат Rozetka без offset Kyiv є явним припущенням: часовий пояс API не визначений у документації.

Для ручної прив’язки виберіть замовлення ліворуч, чек праворуч й натисніть **«Прив’язати вибрані»**. Відкриється порівняння саме цієї пари: збереження лише після «Підтвердити зв’язок». Старий пошук усіх замовлень залишається в «Пов’язане замовлення → Зв’язати / змінити прив’язку». «Відхилити кандидата» та «Відв’язати» зберігають локальне рішення, не змінюючи API. Вибір замовлення не ставить галочку друку чека. Покупець/статус/ТТН у двох таблицях вмикаються прапорцем.

**Точна автоприв’язка** використовує фіскальний документ, не суму/дату. Перевірений UUID, URL Checkbox або фіскальний код із підтвердженим контекстом каси/організації та однозначністю заповнює замовлення без ручного діалогу. Статус — «Точний фіскальний зв’язок» або «Підтверджено вручну»; детальна підстава (UUID / URL / номер) залишається в поясненні. Суперечливі ключі дають конфлікт; ручні рішення й відхилення зберігаються.

**Коли фіскального ключа немає**, основні критерії — точна загальна сума (decimal, до копійки) та **один календарний день за Києвом**. Замовлення має бути створене не пізніше чека. Програма будує спільний набір кандидатів для всіх завантажених чеків і замовлень, незалежно від фільтрів таблиць; відомі інші дати не конкурують. Якщо після перевірок замовленню відповідає тільки один чек і навпаки, пара одразу отримує **«Автозв’язок: унікальна сума»** без обов’язкового ручного підтвердження. Відсутні SKU, ціна позиції або повний кошик не блокують таку пару; брак товарних даних і невідома валюта позначаються як обмеження. Відома інша валюта, невідома сума або дата, суперечливі фіскальні ключі, неповна пагінація й відомі спеціальні оплати не дають нового автозв’язку.

Товари — додаткова перевірка та спосіб розрізнення однакових сум: **збігаються / суперечать / недостатньо даних / завантажуються**. Повні нормалізовані назви й відомі сумарні кількості підсилюють зв’язок до **«Автозв’язок: сума й товари»**. Регістр, пробіли та типографічні лапки/тире нормалізуються; модель, напруга, колір, розмір та роз’єм не стираються. Скорочення або інша мова не є доказом збігу. Однакові позиції агрегуються за назвою незалежно від розбиття рядків, ціни позицій між системами не зобов’язані бути однаковими. SKU не використовується як спільний ключ без доказу спільного простору артикулів. Відомі суперечності блокують призначення. Доставка не додається/віднімається: якщо вона вказана окремо, потрібні товарні дані, що підтверджують `Total = сума товарів`; інакше залишається пояснений кандидат. Нерозібрані знижки та передоплата потребують точного або ручного зв’язку.

**Українські назви Prom:** для всіх позицій програма бере `products[].name_multilang.uk` із самого API замовлень і порівнює з українськими назвами Checkbox. Це не переклад за словником і не правило для окремих товарів. Якщо API не надав придатної української назви, залишається вихідна `name`, без вигадування перекладу. Після оновлення програми один раз натисніть **«Оновити автоприв’язки»**, щоб перечитати старі кешовані назви; ручні зв’язки й історія друку не видаляються. [Перевірка API та регресії](docs/PROM_UKRAINIAN_NAMES_REPORT.md).

Для однакових сум і кількостей назви можуть розрізнити явно різні типи товарів, наприклад USB-розетку й LED-підсвітку. Використовується обмежений словник однозначних назв типів на початку назви; складені назви, комплекти й невідомі слова не класифікуються навмання. Для простих назв із самих слів підтримується перестановка на кшталт «Червоний кабель USB» / «Кабель USB червоний», але не перестановка моделей, чисел чи ролей характеристик. Переклад, скорочення або лише різний текст не доводять відмінність. Зв’язок створюється тільки після перевірки всього графа конкурентів, а не за одним найсхожішим словом. Ціна окремої позиції не замінює загальної суми замовлення. [Перевірки назв і обмеження](docs/NAME_MATCHING_REPORT.md).

Два однакові замовлення різних покупців за один день з одним або двома однаковими чеками залишаються **неоднозначною групою**. Час, ID, порядок API та кількість документів не розподіляють пари навмання. Конкуренти без деталей або з невідомою датою не зникають. Завантажений діапазон містить період чеків і налаштований запас історії; для автоматичної пари дати мають збігатися. Новий конкурент скасовує непідтверджену унікальність; підтверджені вручну й точні фіскальні зв’язки мають пріоритет і можуть бути між різними датами. Ймовірні результати зберігаються в окремому локальному кеші, не записуються як ручні рішення та не змінюють підтверджений пакет друку.

Номери пов’язаних документів з’являються в обох таблицях. Кнопка номера замовлення відкриває його локальні дані; «Відкрити чек» — попередній перегляд офіційного PNG. «Пов’язане замовлення / кандидати» показує причину, кількість конкурентів, покупців, товари та час. Для підтвердження/зміни виберіть пару й натисніть «Прив’язати вибрані»; відхилення залишається доступним у діалозі. Деталі чеків читаються максимум по 100 за операцію, кнопка «Оновити автоприв’язки» продовжує перевірку. F5 основної вкладки цього не запускає. Звіт: [AMOUNT_MATCHING_REPORT.md](docs/AMOUNT_MATCHING_REPORT.md).

Автоматичне оновлення виконується один раз для завантаженого набору чеків: повторний вхід на вкладку не дублює запити. Вихід із вкладки або зняття прапорця скасовує її автоматичну операцію, але не вручну запущене оновлення. Після скасування/помилки натисніть «Оновити замовлення» або повторно увімкніть прапорець; нескінченних повторів немає.

Поки перевірка замовлень неповна, підказка показує цей стан замість підсумку «0 ймовірних». Старі кешовані замовлення з відомою датою поза видимим періодом залишаються в кеші та доступні після зміни/скидання фільтра дат, але не блокують перевірку поточного періоду масовим повторним запитом. Збережені ручні прив’язки, невідомі дати та відсутні у відповіді записи всередині періоду й далі перевіряються. [Причини нульових зв’язків і перевірка правила одного дня](docs/SAME_DAY_MATCHING_REPORT.md).

Якщо Prom додано двічі з тим самим токеном, однакові замовлення показуються **одним рядком** і не конкурують самі із собою під час зіставлення. Перевірка токенів виконується лише локально в пам’яті при відкритті додаткової вкладки та перед оновленням. Ручні прив’язки/відхилення з будь-якої копії враховуються; вихідні ключі й файли не видаляються та не переписуються через об’єднання. Різні токени, невідомі облікові дані, різні маркетплейси або тільки схожі назви не є підставою для такого об’єднання. Підключення залишаються окремими в налаштуваннях, послідовне читання API кожного увімкненого підключення збережено.

Суми Prom на кшталт `300 грн` або `1 234,50 грн` читаються як сума у гривнях, без ділення на 100. Підтримуються позначення `грн`/`грн.`/`UAH`/`₴`; без позначення валюта не вгадується. Суми старого кешу відновлюються з наявного `RawTotal`, кеш видаляти не потрібно. Якщо старий білд не розпізнав також ціни товарів, натисніть «Оновити замовлення», щоб отримати їх повторно для ймовірного зіставлення.

Rozetka читає `prro` зі списку та окремий read-only PRRO URL також для нових замовлень. Відсутнє `prro` у деталях не означає відсутність чека: використовується GET статусу наявного документа. Підтверджений формат URL наразі — `https://api.checkbox.ua/api/v1/receipts/{UUID або fiscal_code}/html` із перевіреними параметрами форматування; URL не відкривається. Фіскальний код без контексту не стає UUID. Для коду з `organization_id` виконується точний read-only пошук Checkbox, залишаючи `self_receipts=true`. Невідомі/короткі/redirect URL не вгадуються.

**Обмеження Prom:** 24.09.2026 перевірено останні замовлення, а потім окремо надане користувачем замовлення з позначкою «Чек виданий». Його деталі та запис у списку повернули HTTP 200, але без UUID, fiscal_code чи URL чека. У публічній GET-схемі відповідного read-поля теж не знайдено. Це не доводить відсутність іншого методу Prom; точний API-зв’язок усе ще потребує уточнення. Новий товарний збіг є лише ймовірним, ручний вибір доступний завжди. Деталі й ненадісланий запит підтримці — у [звіті](docs/FISCAL_LINK_REPORT.md).

Єдиний кандидат за сумою/датою, внутрішній `order_id` Checkbox, serial чека, номер каси, RozetkaPay або перевізник не є точним ключем. Для повернення використовується його власний документ або `related_receipt_id` разом із доведеним зв’язком початкового чека. Зв’язки ізольовані за касиром Checkbox, маркетплейсом і постійним ID підключення. Лічильники завантажених замовлень/автозв’язків і пояснення непідтверджених фіскальних даних видно лише у вкладці інтеграцій.

Недоступність маркетплейсів не блокує друк завантажених чеків. Синхронізація не змінює галочки, порядок уже сформованого пакета або офіційний PNG. F5 зберігає вибір у межах того самого касира. Відсутність чека у списку `self_receipts=true` не доводить, що чек не видавали іншим касиром.

Дані зберігаються в `%LOCALAPPDATA%\CheckboxBatchPrinter\Marketplaces`, незалежно від папки exe:

- `marketplace-settings.json` — назви/постійні ID/увімкнення та строки зберігання; без секретів.
- `Secrets/marketplace-<id>.dpapi` — окремі захищені облікові дані.
- `orders.dpapi` — зашифрований DPAPI кеш покупців/замовлень для поточного Windows-користувача; за замовчуванням 30 днів, налаштування 1–90.
- `receipt-order-links.dpapi` — довготривалі ручні прив’язки/відмови, окремо від кешу.
- `automatic-matches.dpapi` — окремий DPAPI-кеш автоматичних результатів і товарних деталей чеків, із прив’язкою до контексту касира та ключів магазинів. Строк як у кешу замовлень: 30 днів за замовчуванням, 1–90 у налаштуваннях. Обмеження: 8 контекстів, до 5000 деталей і 8 останніх результатів зіставлення на контекст. Не містить паролів, токенів, PNG або даних покупців. Не замінює ручні рішення чи історію друку.

Для ротації токена збережіть існуюче підключення. Для іншого магазину додайте нове підключення, щоб не змішати його локальну історію. Пароль Checkbox і `printed-receipts.json` продовжують зберігатися окремо. DPAPI-файли призначені тому самому Windows-користувачу; копія на інший обліковий запис Windows не є переносним експортом.

API-контракти, джерела та непідтверджені моменти: [docs/MARKETPLACE_API_CONTRACT.md](docs/MARKETPLACE_API_CONTRACT.md). Результати перевірок: [docs/MARKETPLACE_ORDERS_REPORT.md](docs/MARKETPLACE_ORDERS_REPORT.md).

## Збірка та тести

Окрема production-збірка (framework-dependent single-file, власний профіль даних): [інструкція пакування](docs/PRODUCTION_PACKAGING.md), [інструкція користувача](docs/PRODUCTION_README.md). Звичайні development-команди нижче не замінюють production EXE.

### Відновлення з GitHub на чистому комп’ютері

Потрібні **Windows 10/11 x64**, Git і **.NET SDK 8.0.425** (версію закріплено в `global.json`; дозволено новіші patch-релізи тієї самої SDK-серії). Visual Studio не обов’язкова. Під час першої збірки потрібен інтернет для завантаження компонентів .NET. Ніякі файли зі старого білду, локального кешу, токени або паролі для збірки й автоматичних тестів не потрібні.

Актуальний код міститься у гілці **`codex/checkbox-marketplace-orders`**, не в `main`:

```powershell
git clone --branch codex/checkbox-marketplace-orders --single-branch https://github.com/Pvitaly91/CRMapp.git
cd CRMapp
powershell -NoProfile -ExecutionPolicy Bypass -File .\build.ps1
```

Скрипт збирає Release, запускає весь консольний набір регресійних тестів (включно з Windows/WPF/STA) і лише після успіху створює self-contained `win-x64` у `artifacts\win-x64`. На комп’ютері користувача .NET встановлювати не потрібно: переносіть **усю папку збірки**, запускайте `CheckboxBatchPrinter.exe`. Автоматичні тести використовують підставні API/дані й не запускають фізичний друк.

Скрипт не перезаписує непорожню папку. Для повторної збірки задайте нову: `powershell -NoProfile -ExecutionPolicy Bypass -File .\build.ps1 -OutputDirectory artifacts\win-x64-new`. Щоб відновити конкретну ревізію, перед збіркою виконайте `git checkout <commit>` у цій окремій чистій копії.

У Git збережено вихідний код, WPF/XAML-ресурси, проєкти, тести й конфігурацію SDK. Згенеровані `bin`, `obj`, `artifacts`, облікові дані та історія не публікуються. Відновлення **програми** із сорскодів не відновлює особисті дані: їх резервну копію потрібно зберігати окремо. Оновлення папки EXE не видаляє `%LOCALAPPDATA%\CheckboxBatchPrinter`; не видаляйте цю папку під час прибирання старих білдів. DPAPI-секрети прив’язані до облікового запису Windows.

Окремі команди, якщо скрипт не потрібен:

```powershell
dotnet build CheckboxBatchPrinter.sln -c Release
dotnet run --project tests/CheckboxBatchPrinter.Tests -c Release
dotnet publish src/CheckboxBatchPrinter/CheckboxBatchPrinter.csproj -c Release -r win-x64 --self-contained true -o artifacts/win-x64
```

Пароль зберігається у `%LOCALAPPDATA%\CheckboxBatchPrinter\credential.bin` через Windows DPAPI. Налаштування, кеш і логи також залишаються лише в `%LOCALAPPDATA%\CheckboxBatchPrinter`.

Історія успішно переданих на друк чеків зберігається у `%LOCALAPPDATA%\CheckboxBatchPrinter\printed-receipts.json`, тому не втрачається після оновлення або перенесення exe. Записи ізольовано за обліковим контекстом касира та автоматично видаляються через 365 днів. Файл містить лише хеш контексту, ID чека, назву принтера і час; PNG, пароль, токен та дані покупця не записуються.

## Наклейки доставки (development)

На вкладці «Чеки та замовлення» є окремі галочки наклейок, доставка/ТТН, перегляд та «Друк наклейок». Вибір наклейок не позначає фіскальні чеки. «Налаштування → Друк наклейок» зберігає окремий принтер, реальний формат драйвера, масштаб/зміщення/копії та захищений токен Rozetka Delivery.

Нова пошта: збережено офіційну Zebra-форму через явно вибране доступне підключення Rozetka Seller; доступ до ТТН з Prom не гарантований. Додано **експериментальне пряме NP-підключення за відкритим SDK**, без Seller: захищений ключ і прив’язка акаунта до магазину Prom, ручна діагностика конкретної існуючої ТТН за явно задані 1–7 днів, PDFium-перевірка та preview без друку. Ключ вводиться лише локально; реальна перевірка NP очікує його введення, методи ще не підтверджені офіційною документацією. Непідтверджена ідентичність/повнота місць не допускає PDF у пакет. Багатомісцеві документи наразі доступні лише для діагностичного перегляду всіх сторінок. Перевірений одно-місцевий PDF 100×100 можна явно дозволити для пакета поточного сеансу; перед ним PDF читається/перевіряється знову. Документ/права/сумісність перевіряються перед підтвердженням усього змішаного пакета. Одна етикетка — одна сторінка, пакет — один Windows job. Невизначений повтор потребує попередження; статус Windows не підтверджує вихід паперу.

PDFium вбудовано в збірку; сторонній переглядач не потрібен. PDF із персональними даними не записується на диск. Окрема DPAPI-історія наклейок зберігається 365 днів у ShippingLabels профілю відповідного каналу й не змінює історію чеків. [Контракти API](docs/SHIPPING_LABELS_API_CONTRACT.md), [перевірки й обмеження](docs/SHIPPING_LABELS_REPORT.md).

## Фізична перевірка

Для end-to-end перевірки потрібні реальні облікові дані Checkbox та встановлений Windows-драйвер принтера. У «Налаштування → Діагностика» доступні перевірка API і тестовий друк. Жоден automated test не виконує фіскальних операцій.
