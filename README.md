У 1.0.70 кнопки повтору й друку вибраних чеків розташовані над відповідними таблицями. «Друк чеків замовлень» друкує лише пов’язані чеки позначених видимих замовлень у порядку таблиці, без вимог до наклейок та доставки. [Поведінка й перевірки](docs/ORDER_RECEIPTS_PRINT_REPORT.md).

У 1.0.69 кнопку «Прив’язати» в таблиці замовлень виділено синім кольором із білим текстом.

У 1.0.68 перегляд за замовчуванням уміщує чек повністю за шириною та висотою вікна. Кнопка «За шириною» збільшує довгий чек для читання з прокруткою; «Увесь чек» повертає повний вигляд. Масштаб друку не змінюється.

У 1.0.67 для замовлення без чека доступна кнопка «Прив’язати»: вибір вільного завантаженого чека з фільтром дат, пошуком за ID чи сумою та переглядом. У двох таблицях чеків дата й час об’єднані, а «Перегляд» розташовано одразу після суми. [Поведінка й перевірки](docs/RECEIPT_PICKER_REPORT.md).

У 1.0.66 прийняті точні прив’язки чеків зберігаються в захищеному кеші та відновлюються після перезапуску до перевірки API. Незмінний обліковий запис, чек і фіскальні дані замовлення перевіряються локально; нові чи суперечливі дані потребують перевірки. [Причина й відновлення](docs/EXACT_LINK_PERSISTENCE_REPORT.md).

У 1.0.65 Rozetka спочатку прив’язується за ID чека Checkbox. Якщо фіскальний ключ ще відсутній, застосовуються правила Prom: сума товарів, той самий день, товари, кількість та відомий спосіб оплати. Після появи фіскального ключа він має пріоритет над попереднім ймовірним зв’язком. [Правила та перевірки](docs/ROZETKA_MATCHING_FALLBACK_REPORT.md).

У 1.0.63 сума замовлення Rozetka береться з вартості товарів після знижки без доставки. Доставка зберігається окремо, тому товари на 390 грн із доставкою 49 грн зіставляються з товарним чеком на 390 грн. [Причина та перевірки](docs/ROZETKA_GOODS_TOTAL_REPORT.md).

У 1.0.62 готові зв’язки Prom і Rozetka залишаються видимими під час «Оновити все». Уже перевірені фіскальні пари повторно використовуються в поточному сеансі; новий пошук виконується для незв’язаних або змінених документів. Оновлення статусу замовлення чи посилки не прибирає точний зв’язок. [Поведінка та перевірки](docs/ESTABLISHED_LINK_REFRESH_REPORT.md).

У 1.0.61 заміна токена Prom, Rozetka або ключа Нової пошти оновлює наявне підключення зі збереженням історії; повторне натискання кнопки налаштування не створює копій. Checkbox і Rozetka Delivery також використовують наявні налаштування. Фіскальний номер із PRRO Rozetka тепер перевіряється через авторизований пошук Checkbox, навіть коли Seller не передав дані каси. [Перевірки налаштувань і точного зв’язку](docs/SINGLE_CONNECTION_AND_FISCAL_LOOKUP_REPORT.md).

У 1.0.59 Prom також захищений від масових повторних помилок. Після помилок доступу, ліміту, сервера чи мережі запити з тим самим токеном призупиняються щонайменше на 5 хвилин, довший `Retry-After` враховується. Невдалий список більше не запускає сотні перевірок старих замовлень. [Поведінка й перевірки](docs/PROM_RETRY_PROTECTION_REPORT.md).

Актуальна версія — **1.0.71** у гілці [`codex/checkbox-marketplace-orders`](https://github.com/Pvitaly91/CRMapp/tree/codex/checkbox-marketplace-orders). Служби завантажуються паралельно; однакові підключення читаються один раз, відомі UUID Rozetka повторно використовуються, додаткова історія за замовчуванням — 0 днів. Вихідний код, ресурси, тести та скрипти для повного відновлення програми з GitHub збережені в цій гілці. [Відновлення, збірка й прибирання](docs/RECOVERY_AND_CLEANUP.md).

Чеки, видані через Rozetka, отримують точний зв’язок за UUID з документованого PRRO-посилання, через `type=link`, включно з URL старого API-домену Checkbox. [Реалізація й перевірка на робочій парі](docs/ROZETKA_EXACT_RECEIPT_ID_REPORT.md).

Накладні Rozetka Delivery із замовлень Rozetka можна отримувати й друкувати через збережене підключення Seller без окремого ключа Delivery. [Джерело, перевірки та межі доступу](docs/ROZETKA_SELLER_DELIVERY_REPORT.md).

Локальна WPF-програма для Windows 10/11, яка завантажує **вже існуючі** фіскальні чеки через офіційний Checkbox API й пакетно друкує їх офіційні PNG-копії.

**Prom/Rozetka — необов’язковий додатковий модуль.** Для отримання, перегляду та друку достатньо налаштувати тільки Checkbox і принтер. Чек без замовлення — звичайний повноцінний чек.

**Зіставлення у версії 1.0.21:** новий пошук виконується лише серед замовлень і чеків без зв’язку. Уже знайдені автозв’язки зберігаються після оновлення, фонового циклу та перезапуску; їхні товари не порівнюються повторно з новими документами. Збережені пари залишаються ймовірними. Ручні рішення, відв’язування та точні фіскальні дані мають пріоритет; зміна власної суми, товарів чи ключових даних документа скидає застарілу пару. [Реалізація та перевірки](docs/UNLINKED_ORDERS_MATCHING_REPORT.md).

Програма не створює, не фіскалізує і не змінює чеки або зміни. У коді відсутні виклики write-endpoint-ів Checkbox, окрім `cashier/signin`, потрібного для отримання JWT.

## Фоновий режим (1.0.7)

У «Налаштування → Фоновий режим» можна ввімкнути автоматичне оновлення (типово кожні 2 хвилини; 1/2/5/10), обрати робочий період чеків (типово 7 днів), залишення в треї, запуск із Windows та прихований старт. Після запуску програма спершу показує захищений локальний кеш, а потім читає Checkbox і ввімкнені Prom/Rozetka. Вкладка, видимість вікна та календар не керують циклом. Фон не друкує, не створює чеків/ТТН і не змінює замовлень.

Якщо ввімкнено «Залишати в треї», X приховує вікно. Подвійний клік на значку CRMapp його відкриває; меню значка має «Оновити зараз», паузу, налаштування й повний вихід. Звичайне завершення Windows не підмінюється приховуванням. Повторний запуск того самого Windows-користувача, каналу та кореня даних відкриває чинний екземпляр. Development і Production ізольовані. Автозапуск створюється **лише після вибору користувача** у власному HKCU Run-записі каналу та використовує фактичний EXE із `--background`; тестові збірки не реєструють його.

«Сповіщати Windows про нові замовлення» ввімкнено за замовчуванням. Після успішного фонового читання нові замовлення Prom/Rozetka об’єднуються в одне системне сповіщення з номерами замовлень; натискання відкриває CRMapp. Перший повний список нового магазину стає тихою базою, без повідомлень про давню історію. Захищений журнал `Marketplaces/order-notifications.dpapi` запобігає повторам після перезапуску. Вимкнені сповіщення не накопичуються. Windows може приховати повідомлення через власні налаштування сповіщень або «Не турбувати»; програма ці налаштування не змінює.

Список чеків зберігається в `receipts.dpapi` для облікового контексту касира: метадані, перевірений діапазон, час і відбитки; PNG у ньому немає. Замовлення, ручні рішення, автозв’язки й історія друку залишаються у своїх попередніх сховищах. Кешовані дані не позначаються як щойно перевірені. Зміна календаря поза завантаженим діапазоном запускає читання потрібних чеків, не змінюючи фонового робочого періоду. «Сьогодні» переходить на новий день за Києвом, але явно вибраний історичний діапазон не перемикається. Подробиці й межі перевірки: [BACKGROUND_SYNC_REPORT.md](docs/BACKGROUND_SYNC_REPORT.md).

## API

- Production host: `https://api.checkbox.ua`
- Авторизація: `POST /api/v1/cashier/signin`
- Пошук: `GET /api/v1/receipts/search`
- Зображення: `GET /api/v1/receipts/{receipt_id}/png`
- Офіційні джерела: [інтеграція](https://checkbox.ua/api-integration/), [Swagger](https://api.checkbox.ua/api/docs), [ReDoc](https://api.checkbox.ua/api/redoc)

Пошук завантажує тільки чеки поточного касира (`self_receipts=true`). Кілька вибраних чеків друкуються одним завданням Windows із проміжком приблизно 2 мм і розділювальною рискою. Довгі пакети розбиваються між цілими чеками на сторінки, що вміщуються у формат драйвера; порядок зберігається, службові сторінки не додаються. Перед друком перевіряється допустима довжина, кожний чек передається один раз, кількість копій — 1. Деталі: [RECEIPT_BATCH_PAGING_REPORT.md](docs/RECEIPT_BATCH_PAGING_REPORT.md). Над чеком із точним, ручним або ймовірним зв’язком друкується невеликий рядок «Замовлення №…», поруч — наявні ТТН Нової пошти / Rozetka Delivery. Довгий рядок переноситься; кілька різних ТТН друкуються без дублів. За відсутності ТТН залишається тільки номер замовлення. Чек без зв’язку друкується без цього рядка й додаткового відступу. Номер і ТТН фіксуються разом із підтвердженим набором чеків та показуються в підтвердженні; офіційний PNG не змінюється. Успішно передані на друк рядки виділяються зеленим і мають статус «Надруковано». Деталі перевірки: [PRINT_ORDER_NUMBER_REPORT.md](docs/PRINT_ORDER_NUMBER_REPORT.md).

У «Налаштування → Checkbox» введіть логін та особистий пароль **касира** Checkbox. Вони можуть відрізнятися від даних входу до особистого кабінету. Поточна схема API визначає для `/api/v1/cashier/signin` саме ці два поля; ключ інтеграції для цього запиту не вимагається. Якщо сервер поверне HTTP 403, програма покаже відому причину (невірні дані касира, ключ доступу або деактивований касир), не записуючи пароль у журнал. Невдала перевірка не замінює збережений пароль.

## Вкладки та оновлення

Поля «Дата від / Дата до» одразу фільтрують **і чеки, і замовлення** за календарною датою Києва. Для чеків поза завантаженим діапазоном програма запускає читання після зміни дат; старий фоновий діапазон не пересувається. Порожня дата знімає відповідну межу. Приховані рядки, галочки та архів не видаляються; усі завантажені конкуренти продовжують враховуватися в зіставленні.

Кнопка **«Оновити все»** та **F5** оновлюють чеки Checkbox, замовлення з автоприв’язками й накладні Нової пошти та Rozetka Delivery за вибраний період незалежно від активної вкладки. Помилка одного сервісу не зупиняє інші; стан служб доступний у підказці кнопки. Зміна дат скасовує поточний цикл. Після помилки Checkbox нові автоприв’язки не створюються на основі застарілого списку чеків. Звіт: [UNIFIED_REFRESH_REPORT.md](docs/UNIFIED_REFRESH_REPORT.md).

Галочка в заголовку першої колонки кожної таблиці позначає доступні видимі рядки; повторне натискання знімає всі галочки цієї таблиці, включно з прихованими. Частковий вибір показано рискою. Вибір у таблицях незалежний. **«Чеки за сьогодні»** встановлює сьогоднішній день за Києвом, скидає пошук/тип чека й одразу завантажує список. Календарна кнопка «Сьогодні» працює так само. Після успішного передавання на друк галочки переданих чеків знімаються у вкладці, з якої запущено друк; історія та зелена позначка залишаються.

Після запуску відкривається **«Усі чеки»**: усі доступні поточному касиру чеки за обраний період, незалежно від магазинів, прив’язок, стану API чи кешу маркетплейсів. Пошук тут використовує тільки дані самого чека. Доступні фільтр типу, сортування, галочка з першого кліку, офіційний PNG, пакетний друк та історія. `self_receipts=true` і наявні права доступу збережені. **«Усі накладні»** завантажує документи перевізників незалежно від наявності замовлень і дозволяє перегляд та друк наклейок.

**«Чеки та замовлення»** містить дві таблиці поруч: ліворуч **завантажені замовлення за спільним фільтром дат** увімкнених Prom/Rozetka-магазинів, включно з непов’язаними; праворуч — чеки Checkbox. Замовлення мають незалежні пошук/фільтр і показують точні, ручні та ймовірні зв’язки. Вертикальний розділювач між таблицями можна пересувати ліворуч/праворуч, змінюючи ширину панелей; кожна таблиця має власну прокрутку. Локальний кеш читається при запуску; за ввімкненого фону замовлення й зв’язки оновлюються незалежно від відкритої вкладки. F5 та «Оновити все» оновлюють усі служби за обраний період. Для самого списку замовлень успішний вхід у Checkbox або наявність чеків не потрібні. Це всі **завантажені/кешовані** замовлення, а не обіцянка отримати всю історію магазину одним запитом. Для вимкнення модуля зніміть «Увімкнути підключення»: секрети, кеш і ручні рішення залишаться збереженими.

Стан оновлення, пояснення точних/ймовірних зв’язків, кількість/область завантажених замовлень і обмеження поточного касира сховані під кнопкою **ⓘ** біля прапорця автоприв’язки. Наведіть на неї курсор, щоб прочитати актуальні повідомлення; постійного великого текстового блока над таблицями немає. Над таблицею замовлень лише один рядок: поле пошуку, фільтр і «Прив’язати вибрані». У дуже вузькій панелі цей рядок прокручується горизонтально, не переноситься й не приховує кнопки назавжди.

Кожна вкладка має окремі пошук, фільтри, сортування, поточний рядок і позначки друку. Період завантаження Checkbox, самі рядки/PNG та історія спільні; дубльованих серверних запитів чи сховищ для вкладок немає. Галочка в заголовку таблиці, Ctrl+A, Ctrl+P і нижні кнопки діють на **активну** вкладку. Зняття всього вибору прибирає також її приховані позначки, але не змінює позначки іншої вкладки.

Друк бере лише позначені видимі чеки в порядку активної таблиці. Підтвердження показує точний список і кількість прихованих позначок, які не потрапили в пакет. Принтер, IDs та порядок фіксуються: перемикання вкладки чи завершення синхронізації не змінює пакет і не дозволяє паралельно запустити другий. Стан друку одразу спільний для обох таблиць, але галочки між ними не копіюються. Прив’язка до замовлення для друку не потрібна.

## Необов’язкові замовлення Prom.ua та Rozetka

Для однакової суми й дати додатково порівнюється **сумарна кількість товарних одиниць** у повних кошиках. Наприклад, два замовлення по 201 грн із 1 та 2 одиницями можна розрізнити за відповідними чеками. Це сума `Quantity`, не число рядків: один рядок ×2 та два рядки ×1 мають однакову кількість. Якщо цей критерій усунув конкурентів і пара стала взаємно унікальною, статус — «Автозв’язок: сума й кількість товарів» (або сильніший «сума й товари», якщо підтверджено також назви). Однакова кількість не доводить тотожність товарів. Невідомі, дробові, неповні або скориговані кількості не використовуються для виключення конкурента; ручні й фіскальні зв’язки зберігають пріоритет. Зміна версії алгоритму інвалідує старі результати автокешу, але зберігає придатні деталі чеків. [Звіт перевірки кількості](docs/QUANTITY_MATCHING_REPORT.md).

У «Налаштування → Маркетплейси» додайте магазин, увімкніть підключення і введіть секрети **тільки локально**:

- Prom — API-токен з мінімальним правом читання замовлень.
- Rozetka — API-токен із кабінету продавця «Налаштування → Безпека API»; запити використовують `Authorization: Bearer`. Логін і пароль кабінету не використовуються.

Натисніть «Перевірити підключення», потім «Зберегти». Перейдіть на «Чеки та замовлення» — оновлення почнеться автоматично. Для прив’язки додатково завантажте чеки Checkbox. За замовчуванням завантажується обраний календарний період без додаткової історії. Запас історії задається в налаштуваннях; зіставлення за сумою працює тільки в межах дати чека. Фактичний діапазон, останнє успішне оновлення і неповний результат показуються у вкладці інтеграцій. Календар використовує час Києва. Для дат Rozetka без offset Kyiv є явним припущенням: часовий пояс API не визначений у документації.

Для ручної прив’язки виберіть замовлення ліворуч, чек праворуч й натисніть **«Прив’язати вибрані»**. Відкриється порівняння саме цієї пари: збереження лише після «Підтвердити зв’язок». Старий пошук усіх замовлень залишається в «Пов’язане замовлення → Зв’язати / змінити прив’язку». «Відхилити кандидата» та «Відв’язати» зберігають локальне рішення, не змінюючи API. Вибір замовлення не ставить галочку друку чека. Покупець/статус/ТТН у двох таблицях вмикаються прапорцем.

**Точна автоприв’язка** використовує фіскальний документ, не суму/дату. Перевірений UUID, URL Checkbox або фіскальний код із підтвердженим контекстом каси/організації та однозначністю заповнює замовлення без ручного діалогу. Статус — «Точний фіскальний зв’язок» або «Підтверджено вручну»; детальна підстава (UUID / URL / номер) залишається в поясненні. Суперечливі ключі дають конфлікт; ручні рішення й відхилення зберігаються.

**Коли фіскального ключа немає**, основні критерії — точна загальна сума (decimal, до копійки) та **один календарний день за Києвом**. Замовлення має бути створене не пізніше чека. Програма будує спільний набір кандидатів для всіх завантажених чеків і замовлень, незалежно від фільтрів таблиць; відомі інші дати не конкурують. Якщо після перевірок замовленню відповідає тільки один чек і навпаки, пара одразу отримує **«Автозв’язок: унікальна сума»** без обов’язкового ручного підтвердження. Відсутні SKU, ціна позиції або повний кошик не блокують таку пару; брак товарних даних і невідома валюта позначаються як обмеження. Відома інша валюта, невідома сума або дата, суперечливі фіскальні ключі, неповна пагінація й відомі спеціальні оплати не дають нового автозв’язку.

Товари — додаткова перевірка та спосіб розрізнення однакових сум: **збігаються / суперечать / недостатньо даних / завантажуються**. Повні очищені назви й відомі сумарні кількості підсилюють зв’язок до **«Автозв’язок: сума й товари»**. Регістр та пробіли нормалізуються, спеціальні символи прибираються тільки з ключа порівняння; літери, цифри й порядок слів зберігаються. Скорочення або інша мова не є доказом збігу. Однакові очищені позиції агрегуються незалежно від розбиття рядків, ціни позицій між системами не зобов’язані бути однаковими. SKU не використовується як спільний ключ без доказу спільного простору артикулів. Відомі суперечності блокують призначення. Доставка не додається/віднімається: якщо вона вказана окремо, потрібні товарні дані, що підтверджують `Total = сума товарів`; інакше залишається пояснений кандидат. Нерозібрані знижки та передоплата потребують точного або ручного зв’язку.

**Українські назви Prom:** для всіх позицій програма бере `products[].name_multilang.uk` із самого API замовлень і порівнює з українськими назвами Checkbox. Це не переклад за словником і не правило для окремих товарів. Якщо API не надав придатної української назви, залишається вихідна `name`, без вигадування перекладу. Після оновлення програми один раз натисніть **«Оновити все»**, щоб перечитати старі кешовані назви; ручні зв’язки й історія друку не видаляються. [Перевірка API та регресії](docs/PROM_UKRAINIAN_NAMES_REPORT.md).

**Очищені повні назви для всіх товарів Prom/Rozetka:** перед порівнянням прибираються апострофи (зокрема `ʼ`), `?`, лапки, дефіси, дужки, стрілки, `×`, емодзі та інші символи, які не є літерами/цифрами/пробілами. Наприклад, `Роз’єм XT60H-F` і `Роз?єм XT60HF` стають `РОЗЄМ XT60HF`. Між цифровими фрагментами замість символів залишається пробіл: `1.5` → `1 5`, не `15`; `12/24` → `12 24`, не `1224`. Символ Ом та його варіанти `Ω` / `Ω` / `ω` також прибираються з ключа порівняння; інші літери не вгадуються за `?`. Оригінальні назви в API-даних, кеші, таблицях і друці не переписуються.

Порівнюються всі очищені назви та сумарні кількості по кожній із них; порядок рядків і розбиття одного товару на кілька рядків не важливі. Словника типів, перекладу або пошуку схожих слів немає. Різні очищені назви у структурно повних кошиках виключають пару; відсутні або порожні після очищення назви, неповний/завантажуваний кошик залишають товарну невизначеність. Якщо два замовлення після очищення стали однаковими, обидва лишаються конкурентами — час/ID не обирають переможця. Очищення не доводить фізичної тотожності: наприклад, `AB-12`/`AB12` і цифрові записи `1/5`/`1.5` можуть мати однаковий ключ. Зв’язок і далі ймовірний і вимагає взаємної унікальності цілого графа, суми та дати. Скорочення, переклад, інші літери/цифри або додані слова не ігноруються; за потреби використовуйте ручний зв’язок. Ціна окремої позиції не замінює загальну суму. Чеки ще не підключених маркетплейсів залишаються в перевірці; джерело не визначається за оплатою. [Перевірки й обмеження](docs/NAME_MATCHING_REPORT.md).

Два однакові **ще не пов’язані** замовлення різних покупців за один день з одним або двома однаковими вільними чеками залишаються **неоднозначною групою**. Час, ID, порядок API та кількість документів не розподіляють пари навмання. Конкуренти без деталей або з невідомою датою не зникають. Завантажений діапазон містить період чеків і налаштований запас історії; для нової автоматичної пари дати мають збігатися. Новий конкурент не скасовує вже знайдений автозв’язок: його замовлення і чек виключено з нового пошуку. Підтверджені вручну й точні фіскальні зв’язки мають пріоритет і можуть бути між різними датами. Ймовірні результати зберігаються в окремому локальному кеші, не записуються як ручні рішення та не змінюють підтверджений пакет друку.

**Оплата — лише після товарів:** спершу дата та сума, потім повні назви й кількість. Оплата розрізняє лише неоднозначну групу **однакових повних кошиків**, де всі залишені товарні пари підтверджені. Якщо є конкурент без повних назв/кількостей або ще завантажуваний кошик, оплата його не виключає. Встановлена за товарами пара зберігає підставу «сума й товари», а не «оплата».

Для таких однакових кошиків Prom «Пром-оплата» зіставляється з явним `RozetkaPay` у чеку, а стандартна «Післяплата» / «Наложенный платеж» — з `NovaPay` лише за однозначно вказаної Нової пошти. Явні назви самих провайдерів також підтримуються. Це обмежене ймовірне зіставлення, не визначення маркетплейсу або факту отримання коштів. Платежі чека мають бути позитивними, повністю покривати суму та належати одному відомому провайдеру. Загальні «картка/безготівково», невідомі/змішані/часткові платежі й післяплата іншого перевізника не виключають конкурентів. Остаточний граф має бути взаємно унікальним; статус — «Автозв’язок: сума й оплата». Зміна версії алгоритму перераховує застарілі висновки, зберігаючи придатні деталі та ручні рішення. [Регресії](docs/NAME_MATCHING_REPORT.md).

Номери пов’язаних документів з’являються в обох таблицях. Кнопка номера замовлення відкриває його локальні дані; «Відкрити чек» — попередній перегляд офіційного PNG. «Пов’язане замовлення / кандидати» показує причину, кількість конкурентів, покупців, товари та час. Для підтвердження/зміни виберіть пару й натисніть «Прив’язати вибрані»; відхилення залишається доступним у діалозі. Деталі чеків читаються максимум по 100 за операцію; «Оновити все» або F5 продовжує перевірку. Звіт: [AMOUNT_MATCHING_REPORT.md](docs/AMOUNT_MATCHING_REPORT.md).

Автоматичне оновлення виконується один раз для завантаженого набору чеків: повторний вхід на вкладку не дублює запити. Вихід із вкладки або зняття прапорця скасовує її автоматичну операцію, але не вручну запущене оновлення. Після скасування/помилки натисніть «Оновити все» або повторно увімкніть прапорець; нескінченних повторів немає.

Поки перевірка замовлень неповна, підказка показує цей стан замість підсумку «0 ймовірних». Старі кешовані замовлення з відомою датою поза видимим періодом залишаються в кеші та доступні після зміни/скидання фільтра дат, але не блокують перевірку поточного періоду масовим повторним запитом. Збережені ручні прив’язки, невідомі дати та відсутні у відповіді записи всередині періоду й далі перевіряються. [Причини нульових зв’язків і перевірка правила одного дня](docs/SAME_DAY_MATCHING_REPORT.md).

Якщо Prom додано двічі з тим самим токеном, однакові замовлення показуються **одним рядком** і не конкурують самі із собою під час зіставлення. Перевірка токенів виконується лише локально в пам’яті при відкритті додаткової вкладки та перед оновленням. Ручні прив’язки/відхилення з будь-якої копії враховуються; вихідні ключі й файли не видаляються та не переписуються через об’єднання. Різні токени, невідомі облікові дані, різні маркетплейси або тільки схожі назви не є підставою для такого об’єднання. Ідентичні підключення читаються один раз; незалежні служби завантажуються паралельно.

Суми Prom на кшталт `300 грн` або `1 234,50 грн` читаються як сума у гривнях, без ділення на 100. Підтримуються позначення `грн`/`грн.`/`UAH`/`₴`; без позначення валюта не вгадується. Суми старого кешу відновлюються з наявного `RawTotal`, кеш видаляти не потрібно. Якщо старий білд не розпізнав також ціни товарів, натисніть «Оновити все», щоб отримати їх повторно для ймовірного зіставлення.

Rozetka читає `prro` зі списку та окремий read-only PRRO URL через `type=link` також для нових замовлень. Відсутнє `prro` у деталях не означає відсутність чека: використовується GET статусу наявного документа. Перевіряються точні API-домени `api.checkbox.ua` та `api.checkbox.in.ua` і шлях `/api/v1/receipts/{UUID або fiscal_code}/html` із дозволеними параметрами форматування; URL не відкривається. Фіскальний код сам собою не стає UUID. Для коду з підтвердженим контекстом або документованого поля Seller `prro.prro_receipt_fiscal_code` виконується точний авторизований пошук Checkbox, залишаючи `self_receipts=true`. Невідомі/короткі/redirect URL не вгадуються.

**Обмеження Prom:** 24.09.2026 перевірено останні замовлення, а потім окремо надане користувачем замовлення з позначкою «Чек виданий». Його деталі та запис у списку повернули HTTP 200, але без UUID, fiscal_code чи URL чека. У публічній GET-схемі відповідного read-поля теж не знайдено. Це не доводить відсутність іншого методу Prom; точний API-зв’язок усе ще потребує уточнення. Новий товарний збіг є лише ймовірним, ручний вибір доступний завжди. Деталі й ненадісланий запит підтримці — у [звіті](docs/FISCAL_LINK_REPORT.md).

Єдиний кандидат за сумою/датою, внутрішній `order_id` Checkbox, serial чека, номер каси, RozetkaPay або перевізник не є точним ключем. Для повернення використовується його власний документ або `related_receipt_id` разом із доведеним зв’язком початкового чека. Зв’язки ізольовані за касиром Checkbox, маркетплейсом і постійним ID підключення. Лічильники завантажених замовлень/автозв’язків і пояснення непідтверджених фіскальних даних видно лише у вкладці інтеграцій.

Недоступність маркетплейсів не блокує друк завантажених чеків. Синхронізація не змінює галочки, порядок уже сформованого пакета або офіційний PNG. F5 зберігає вибір у межах того самого касира. Відсутність чека у списку `self_receipts=true` не доводить, що чек не видавали іншим касиром.

Дані робочої версії (Production) зберігаються в `%LOCALAPPDATA%\CheckboxBatchPrinter-Production\Marketplaces`, незалежно від папки exe:

- `marketplace-settings.json` — назви/постійні ID/увімкнення та строки зберігання; без секретів.
- `Secrets/marketplace-<id>.dpapi` — окремі захищені облікові дані.
- `orders.dpapi` — зашифрований DPAPI кеш покупців/замовлень для поточного Windows-користувача; за замовчуванням 30 днів, налаштування 1–90.
- `receipt-order-links.dpapi` — довготривалі ручні прив’язки/відмови, окремо від кешу.
- `automatic-matches.dpapi` — окремий DPAPI-кеш автоматичних результатів і товарних деталей чеків, із прив’язкою до контексту касира та ключів магазинів. Строк як у кешу замовлень: 30 днів за замовчуванням, 1–90 у налаштуваннях. Обмеження: 8 контекстів, до 5000 деталей і 8 останніх результатів зіставлення на контекст. Не містить паролів, токенів, PNG або даних покупців. Не замінює ручні рішення чи історію друку.

Для ротації токена збережіть існуюче підключення. Для іншого магазину додайте нове підключення, щоб не змішати його локальну історію. Пароль Checkbox і `printed-receipts.json` продовжують зберігатися окремо. DPAPI-файли призначені тому самому Windows-користувачу; копія на інший обліковий запис Windows не є переносним експортом.

API-контракти, джерела та непідтверджені моменти: [docs/MARKETPLACE_API_CONTRACT.md](docs/MARKETPLACE_API_CONTRACT.md). Результати перевірок: [docs/MARKETPLACE_ORDERS_REPORT.md](docs/MARKETPLACE_ORDERS_REPORT.md).

## Збірка та тести

Окрема production-збірка (framework-dependent single-file, власний профіль даних): [інструкція пакування](docs/PRODUCTION_PACKAGING.md), [інструкція користувача](docs/PRODUCTION_README.md). Звичайні development-команди нижче не замінюють production EXE.

### Відновлення з GitHub на чистому комп’ютері

Потрібні **Windows 10/11 x64**, Git і **.NET SDK 8.0.425** (версію закріплено в `global.json`; дозволено новіші patch-релізи тієї самої SDK-серії). Visual Studio не обов’язкова. Під час першої збірки потрібен інтернет для завантаження компонентів .NET. Ніякі файли зі старого білду, локального кешу, токени або паролі для збірки й автоматичних тестів не потрібні.

Актуальний код міститься у гілці **`codex/checkbox-marketplace-orders`**, не в `main`:

```powershell
git clone --branch codex/checkbox-marketplace-orders --single-branch https://github.com/Pvitaly91/CRMapp.git
cd CRMapp
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\Build-Production.ps1
```

Скрипт перевіряє чистий Git-стан, збирає й тестує канали Development і Production та створює перевірений однофайловий Production EXE у `artifacts\production\<version>-<sha>\app` і ZIP поруч. Усі ресурси, включно з PDFium та іконкою, беруться з відстежуваних джерел і NuGet-залежностей. Для запуску потрібний .NET Desktop Runtime 8 x64; перевірка й встановлення доступні в пакеті через `Ensure-DesktopRuntime.ps1`. Автоматичні тести використовують підставні API/дані та не виконують фізичний друк. Під час перевірки пакування CRMapp має бути закритий через трей → «Вийти».

Релізи незмінні: для повторного пакування тієї самої ревізії спочатку збережіть потрібний пакет поза його вихідною папкою. Щоб відновити конкретну ревізію, перед збіркою виконайте `git checkout <commit>` в окремій чистій копії. Попередня self-contained Development-збірка доступна через `build.ps1`; переносити потрібно всю її вихідну папку.

У Git збережено вихідний код, WPF/XAML-ресурси, проєкти, тести й конфігурацію SDK. Згенеровані `bin`, `obj`, `artifacts`, облікові дані та історія не публікуються. Відновлення **програми** із сорскодів не відновлює особисті дані: їх резервну копію потрібно зберігати окремо. Оновлення папки EXE не видаляє `%LOCALAPPDATA%\CheckboxBatchPrinter-Production`; не видаляйте цю папку під час прибирання старих білдів. DPAPI-секрети прив’язані до облікового запису Windows.

Окремі команди, якщо скрипт не потрібен:

```powershell
dotnet build CheckboxBatchPrinter.sln -c Release
dotnet run --project tests/CheckboxBatchPrinter.Tests -c Release
dotnet publish src/CheckboxBatchPrinter/CheckboxBatchPrinter.csproj -c Release -r win-x64 --self-contained true -o artifacts/win-x64
```

У робочій версії пароль зберігається у `%LOCALAPPDATA%\CheckboxBatchPrinter-Production\credential.bin` через Windows DPAPI. Налаштування, кеш і логи також залишаються в `%LOCALAPPDATA%\CheckboxBatchPrinter-Production`. Канал Development використовує окрему папку `%LOCALAPPDATA%\CheckboxBatchPrinter`.

Історія успішно переданих на друк чеків зберігається у `%LOCALAPPDATA%\CheckboxBatchPrinter-Production\printed-receipts.json`, тому не втрачається після оновлення або перенесення exe. Записи ізольовано за обліковим контекстом касира та автоматично видаляються через 365 днів. Файл містить лише хеш контексту, ID чека, назву принтера і час; PNG, пароль, токен та дані покупця не записуються.

## Наклейки доставки (development)

У версії 1.0.15 вибрані ТТН Нової пошти завантажуються **одним PDF-запитом на NP-акаунт**, без читання списку накладних. Сторінки зіставляються з ТТН локально, включно з кількома етикетками одного відправлення. Фіксованого очікування 2 секунди немає; пауза застосовується лише після відповіді НП про обмеження частоти. Час відповіді сервера не гарантується.

На вкладці «Чеки та замовлення» є окремі галочки наклейок, доставка/ТТН, перегляд та «Друк наклейок». Вибір наклейок не позначає фіскальні чеки. У «Налаштування → Друк наклейок» на основному екрані залишено принтер, реальний формат драйвера, копії та одне захищене поле API-ключа Нової пошти для магазину Prom. Якщо магазин один, вибирати акаунти/прив’язки не потрібно: введіть ключ і натисніть «Зберегти». Якщо магазинів кілька, виберіть потрібний; чернетки ключів зберігаються окремо. Порожнє поле залишає старий ключ. Масштаб/зміщення/орієнтація, окремий токен Rozetka Delivery та Seller перенесені в згорнуті «Розширені налаштування». Дубльований редактор NP-акаунтів, ключа, прив’язок і дат видалено; наявні захищені дані збережено.

Нова пошта: збережено офіційну Zebra-форму через явно вибране доступне підключення Rozetka Seller; доступ до ТТН з Prom не гарантований. Пряме NP-підключення використовує **досліджений відкритий SDK**, захищений ключ і явну прив’язку акаунта до магазину Prom. Ключ вводиться лише в основному полі налаштувань. «Друк наклейок» отримує один PDF усіх вибраних ТТН цього акаунта; окремий дозвіл для кожної ТТН і пошук за останні 7 днів не потрібні. Усі повернуті сторінки розподіляються за надрукованим номером ТТН, а не за порядком відповіді. Відсутня ТТН, стороння/невпізнана сторінка або непідтримуваний формат зупиняють пакет. Якщо замовлення містить кількість місць, нестача сторінок також блокує друк; без цієї кількості включаються всі отримані сторінки, але повнота місць не оголошується доведеною. Остаточне рішення — перегляд і підтвердження всього пакета. Окреме вікно діагностики, як і раніше, читає останні 7 днів створення ТТН; його перевірка не запускає друк і не зберігає налаштування. Один реальний документ перевірено у 1.0.10; новий пакетний маршрут перевірено синтетично, не на реальних документах. Одна етикетка — одна сторінка, пакет — один Windows job. Невизначений повтор потребує попередження; статус Windows не підтверджує вихід паперу.

Замовлення з ТТН, яку успішно передано в чергу друку Windows, підсвічуються зеленим так само, як надруковані чеки. Позначка відновлюється з історії наклейок після запуску та оновлення таблиці, працює для Нової пошти й Rozetka Delivery. Невизначена або невдала спроба сама по собі не дає зеленого кольору; невдалий повтор не стирає попередній успішний друк тієї самої ТТН. Після заміни ТТН враховується історія нової накладної.

PDFium вбудовано в збірку; сторонній переглядач не потрібен. PDF із персональними даними не записується на диск. Окрема DPAPI-історія наклейок зберігається 365 днів у ShippingLabels профілю відповідного каналу й не змінює історію чеків. [Контракти API](docs/SHIPPING_LABELS_API_CONTRACT.md), [перевірки й обмеження](docs/SHIPPING_LABELS_REPORT.md).

## Оновлення production

Для оновлення встановленої production-програми закрийте її через меню трея → «Вийти» та запустіть `powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\Update-Production.ps1`. Скрипт встановить останній готовий production-пакет із `artifacts\production`, створить резервну копію EXE/профілю й збереже історію. Якщо код новіший за пакет, скрипт повідомить версії та запропонує `-Build`, який збере й перевірить поточний закомічений код. `-WhatIf` перевірить готове оновлення без запису, навіть коли програма відкрита. ## Фізична перевірка

Для end-to-end перевірки потрібні реальні облікові дані Checkbox та встановлений Windows-драйвер принтера. У «Налаштування → Діагностика» доступні перевірка API і тестовий друк. Жоден automated test не виконує фіскальних операцій.
