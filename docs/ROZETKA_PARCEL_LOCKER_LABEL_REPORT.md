# Нова Пошта (поштомати) у замовленнях Rozetka — 1.0.49

Збережене замовлення містило ТТН і `delivery_service_name = "Нова Пошта (поштомати)"`, `delivery_service_id = 43660`, джерело `Rozetka.ttn`. Перевірка перевізника розпізнавала лише загальну назву Нової пошти, тому залишала перевізника невідомим і зупиняла підготовку наклейок та спільного друку.

Додано точний варіант назви до `ShippingCarrierNames.FromDocumentedDeliveryField`. Оригінальні поля доставки та ТТН зберігаються. Код 43660 не використовується як окремий ключ визначення перевізника; номер ТТН та його префікс також не є підставою для вгадування. Невідомі назви лишаються невідомими. Нормалізація регістру й крайових пробілів зберігається.

Виправлення працює під час читання вже збережених `OrderShipment`, тому повторне завантаження всіх замовлень не потрібне. Для звичайної ТТН Нової пошти замовлення Rozetka використовується вже наявне джерело `RozetkaSeller.Zebra`; маршрут накладних Rozetka Delivery не змінюється.

12.10.2026 виконано контрольне читання однієї наявної наклейки з чинного Seller-підключення: отримано PDF, 190047 байтів, джерело `RozetkaSeller.Zebra`. Вміст документа, облікові дані та дані отримувача не записувалися у репозиторій. Накладні не створювалися й не змінювалися; принтер не викликався.

Два регресійні сценарії перевіряють назву, регістр/пробіли, JSON старого кешу та справжній адаптер Rozetka. Вони також перевіряють, що числовий `carrier_inner_id`, невідома назва або лише наявність 14-значної ТТН не перетворюються на визначеного перевізника.
