# Довгі пакети чеків — 1.0.52

## Діагностика 12.10.2026

Перевірка локального профілю та журналу Windows виконана лише для читання, без запуску друку, зміни черги, налаштувань драйвера чи історії.

- У проблемному денному пакеті було 20 різних PNG чеків; контрольні суми всіх 20 різні. Чек №4854 для зазначеного користувачем замовлення був 19-м у послідовності завантаження.
- Сумарна висота самих PNG при налаштованій ширині 48 мм — 2558,1 мм. Заголовки з номером замовлення/ТТН та розділювачі додатково збільшували сторінку.
- Драйвер RPP210A USB (RPP210) повідомив максимальну висоту 2527,487 мм через `psk:PageMediaSizeMediaSizeHeight`. Узгоджений roll-формат має розмір приблизно 48,047 × 2527,488 мм.
- Попередня реалізація передавала весь пакет як один необмежений `FixedPage` через `PrintVisual`, без перевірки меж драйвера. Windows зареєструвала для пакета одну сторінку. Це підтверджує перевищення допустимої довжини, але сама подія успішного спулінгу не доводить виходу паперу.
- Для того самого Windows job 18 зафіксовано повторну обробку о 16:09:42 та 16:11:18 за київським часом, в обох подіях `Copies=1`. Нового завдання від програми в цей проміжок немає. Журнал не встановлює точну причину повторної обробки або кількість фізичних дублів; не приписуємо її налаштуванню копій чи діям користувача.

## Виправлення

Пакет чеків обмежується допустимою висотою сторінки драйвера й розбивається між цілими чеками. Сторінки містять різні послідовні частини пакета, передані одним завданням Windows. Заголовки, компактні розділювачі та порядок вибраних замовлень зберігаються; завеликий одиночний чек зупиняє підготовку до передавання принтерам.

Перевірка розміру та повноти відбувається до підтвердження спільного друку й повторно перед передаванням. Кількість копій явно дорівнює 1 без зміни системних налаштувань. Підтверджені Windows передачі не прирівнюються до апаратного підтвердження виходу кожного чека.

Спільний друк отримав журнал із випадковим ідентифікатором пакета, позиціями, номерами замовлень та ID чеків на етапах підготовки й передавання. Ключі, дані покупців і ТТН не записуються. Помилка самого журналу не запускає повторного друку й не перетворює успішне передавання на помилку.

Застосований WPF механізм описано в [Microsoft XpsDocumentWriter](https://learn.microsoft.com/en-us/dotnet/api/system.windows.xps.xpsdocumentwriter?view=windowsdesktop-8.0). Узгодження квитка друку виконується явно: [Write / PrintTicket](https://learn.microsoft.com/en-us/dotnet/api/system.windows.xps.xpsdocumentwriter.write?view=windowsdesktop-8.0).

## Перевірка

Регресійні перевірки охоплюють кілька сторінок, незмінний порядок, кожен чек рівно один раз, цілий останній чек, ліміти драйвера, завеликий одиночний чек, одну копію при іншому типовому налаштуванні та помилки діагностичного журналу. Фізичний друк під час перевірок не запускається.

Пройшли 592/592 тести. Окремо документ XPS записано в тимчасовий файл і прочитано повторно: дві сторінки з власними розмірами, усі 20 номерів і зображень по одному разу. Растрова перевірка підтверджує цілі нижні краї останніх чеків.

Опційна команда тестового runner `--receipt-driver-smoke "RPP210A USB"` читає можливості драйвера й готує лише синтетичний документ: 20 чеків, 2 сторінки висотою 2468,341 і 273,638 мм, правильний порядок, одна копія. Завдання друку не створюється.
