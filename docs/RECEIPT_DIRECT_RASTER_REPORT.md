# Прямий друк чеків RPP210 — 1.0.82

## Причина зміни

Після 1.0.81 користувач підтвердив погіршення чіткості та артефакти між групами по три чеки. Попереднє растрування всієї WPF-сторінки не усунуло проблему на фізичному принтері: документ усе ще проходив XPS/GDI-обробку драйвера, а ціла кількість пікселів розтягувалася назад до дробових розмірів сторінки. Перевірка збереження пікселів усередині XPS не перевіряла подальшу обробку драйвером.

23.10.2026 о 02:05 CRMapp передала п'ять різних чеків групами 3+2, кожен один раз. Windows завершила завдання RPP210 №35 та №36 без помилок; наклейки — окреме завдання №37. Вихідний PNG першого чека, 855×3526 пікселів, чистий. Порожнє поле SeparatorPageFile виключає налаштований у Windows файл-розділювач. Це не встановлює точну причину сторонніх символів у драйвері, USB-передаванні або прошивці.

## Підтверджений формат принтера

[Rongta RPP210](https://www.rongtatech.cn/en/download/rpp210-portable-receipt-printer-product-introduction/) підтримує ESC/POS, головку 384 точки, ширину 48 мм і 8 точок/мм. У встановленому `RPP210ENG.GPD` також зазначено 203×203 DPI, 384 точки, горизонтальні байти та команду `GS v 0` із блоками по 24 рядки. [Офіційний посібник ESC/POS Rongta](https://file.globalso.com/file_manage/4366/20251226/esc-programming-manual.pdf), сторінки 29–30, описує цей формат: звичайний масштаб, старший біт ліворуч, 1 — чорна точка.

За [контрактом Microsoft WritePrinter](https://learn.microsoft.com/en-us/windows/win32/printdocs/writeprinter) RAW-завдання повинне містити готові команди принтера. Передавання PNG, PDF або XPS цим способом не підтримується. Тут передаються лише підготовлені ESC/POS-команди та їхні двійкові растрові дані.

## Реалізація

- Прямий шлях вмикається лише для фактичного драйвера `RPP210`, незалежно від назви черги. Перед створенням завдання драйвер повторно перевіряється на відкритому дескрипторі. Інші моделі використовують наявний шлях друку.
- PNG розкладається на цілу сітку точок. Зображення відповідного розміру зберігається точка в точку; більший PNG зменшується один раз усередненням площі, потім переводиться в чорне/біле. Прозорість накладається на біле тло. Проміжного растру цілої WPF-сторінки, повторного масштабування драйвером і напівтонового растру немає.
- Заголовок замовлення та ТТН раструється окремо. У вихідному потоці немає текстових рядків, шрифтів, команд логотипа чи різака. Кожен блок має точні розміри та кількість байтів. Останній неповний блок не доповнюється сміттям. Після групи подається 16 точок паперу.
- Усі три маршрути залишають групи 3+3+…+залишок. Кожна група — одне завдання Windows. Повна підготовка всього вибраного пакета відбувається перед друком чеків і наклейок.
- RAW-виклики виконуються поза потоком інтерфейсу. Часткове успішне записування продовжується з першого ще не прийнятого байта. Помилка чи скасування зупиняють поточне завдання без повтору або перемикання на інший спосіб. Скасовується лише власне незавершене завдання. Прийняті групи зберігаються в історії до наступної.
- Журнал `receipt.raw.accepted` містить номер завдання Windows, число чеків, розмір потоку та формат. Збій журналу не перетворює прийняте завдання на повтор.

## Перевірки

Development: **788/788** тестів. Окремо пройшла перевірка скомпільованих вікон і прив'язок. Читання встановленого RPP210 через Winspool підтвердило правильний вибір прямого шляху; синтетичні вісім чеків підготовлено як 3+3+2 без створення завдання. Перегляд, відновлений із готового потоку для реального PNG 855×3526, має 384×1624 точки: текст, QR-код і нижній край збережені; перевірено візуально.

Автоматичні тести перевіряють точне збереження всіх бітів зображення 384 точки, зменшення 855 точок, прозорість, нижній край, заголовки, межі блоків по 24 рядки, групи 1/2/3, пошкоджені та надмірні розміри. Окремі підробні Winspool-виклики перевіряють усі стадії помилок, часткове передавання, скасування, відсутність повторів і звільнення дескриптора.

`--receipt-raw-smoke` запускає тести без принтера. `--receipt-raw-driver-smoke "RPP210A USB"` тільки читає драйвер та готує синтетичні завдання 3+3+2. `--receipt-raw-preview <PNG> <output.png>` відновлює картинку з фактичних ESC/POS-байтів для візуальної перевірки. Ці команди не створюють завдань друку й не звертаються до API.

Фізичне усунення артефактів і чіткість на папері залишаються предметом наступної перевірки на принтері користувача. Підтвердження Windows означає прийняття завдання, а не підтвердження кожного надрукованого чека.
