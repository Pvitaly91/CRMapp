# Накладні доставки в Rozetka для замовлень Prom і Bigl

Контракт перевірено 14.10.2026. Через авторизований кабінет Prom отримано дві вже створені накладні без окремого ключа Rozetka Delivery. У CRMapp 1.0.74 додано отримання цих PDF через окрему сесію кабінету для наявного підключення Prom; цей шлях застосовується також до замовлень Bigl, доступних у тому самому кабінеті.

## Використання у CRMapp 1.0.74

У «Налаштування → Маркетплейси» виберіть збережене й увімкнене підключення Prom, натисніть «Увійти в кабінет Prom для накладних», увійдіть у потрібний магазин та натисніть «Зберегти сесію». Використовується Microsoft Edge WebView2 Runtime; за його відсутності програма показує повідомлення з адресою офіційного встановлення. Пароль вводиться лише на сторінці Prom; CRMapp не читає його й не переносить cookies до API-клієнтів. Вхід із телефону/email у Prom підтримується; переходи верхнього рівня за межі HTTPS-доменів Prom блокуються.

Сесія зберігається браузером у приватному профілі поточного каналу програми: `PromCabinet/<SHA256 connection ID>/Browser`. Повторний вхід використовує той самий ID підключення й профіль; API-токен, замовлення та історія не дублюються. Наявність збереженої сесії не означає вічну авторизацію: доступ перевіряється під час завантаження. Після завершення сесії потрібний повторний вхід. Стан підключення та пауза запитів зберігаються окремо без секретних значень.

У таблиці замовлень працюють звичайні «Друк наклейок» і «Друк наклейок і чеків». Перед отриманням PDF фіксуються магазин, ID замовлення, ID способу доставки та ТТН. Якщо в старому кеші немає ID способу доставки — потрібно «Оновити все»; ідентифікатор не вгадується. Числові та рядкові ID з Prom нормалізуються однаково.

Завантаження виконується лише після дії друку/перегляду. У фоновому браузері власна мінімальна сторінка CRMapp виконує той самий GET через `fetch` із браузерною авторизацією. Вона обслуговується локально через WebView2, не є новим серверним API. Дозволений лише точний запит вибраної накладної; перенаправлення не виконуються. PDF залишається в пам’яті. Відповідь зв’язується з поточною операцією через випадковий nonce і точний origin, потім перевіряються MIME, максимум 20 MiB, PDFium, одна сторінка 100 × 100 мм та повна ТТН у видимому текстовому шарі. HTML, ZIP, JSON, невірна ТТН або багатомісний PDF зупиняють друк.

Немає автоматичних повторних спроб чи перебору інших магазинів. HTTP 401/403, сторінка входу або перенаправлення знімають позначку придатної сесії й зупиняють пакет. HTTP 429/5xx призупиняють цей магазин за Retry-After (щонайменше на хвилину), а без нього — на 5 хвилин; тимчасова мережева помилка — на хвилину. Пауза зберігається після перезапуску. Новий явний вхід дає змогу відновити сесію.

## Підтверджений контракт кабінету

Джерело — офіційний [CMSOrderEdit JavaScript](https://my.prom.ua/cloud-cgi/static/cabinet-ui/js/build/uk/cms/CMSOrderEdit_CMSOrderEdit_081b4cee4264168a1a2b.js), адресу якого отримано зі сторінки замовлення. SHA256 завантаженого файлу: `EB0285391C5D4B6D5F68EC9D8ECCC5CDB05279D4EABB4426D73E9F7A6527E6F5`.

За ввімкненого `CS.FUNCTIONALITY.INTEGR_5149_NEW_PDF_PRINT_ENDPOINT` дія `downloadEn` викликає `fM(event, orderId, deliveryOptionId)`:

```http
GET https://my.prom.ua/cabinet/delivery/print_shipment_pdf?order_id=<ID замовлення>&delivery_option_id=<ID способу доставки>
```

Код формує параметри через `URLSearchParams` і виконує звичайний `fetch(url)` без тіла та явно заданого Bearer. Під час перевірки використано поточну авторизовану сесію Prom у браузері; сесійні облікові дані не копіювалися до CRMapp, діагностичних файлів чи журналів.

Обробка відповіді в **JavaScript кабінету**:

| Content-Type | Поведінка кабінету |
|---|---|
| `application/pdf`, `text/html` | `response.blob()` → `URL.createObjectURL()` → відкриття документа |
| `application/zip` | Завантаження архіву; ім'я береться з `Content-Disposition`, якщо доступне |
| `application/json` | Повідомлення про помилку; для `status: "error"` використовується поле `message` |
| Інші типи або неуспішний HTTP-статус | Помилка |

Це перелік поведінки кабінету, а не обіцянка підтримки HTML чи ZIP у CRMapp. Посилання `blob:https://my.prom.ua/...` створюється локально в браузері після отримання відповіді й не є серверною адресою накладної.

У тому ж JavaScript знайдено ще два маршрути:

```http
GET https://my.prom.ua/remote/delivery/rozetka_delivery/get_sticker?order_id=<ID замовлення>&declaration_id=<ТТН>
GET https://my.prom.ua/remote/delivery/rozetka_delivery/init_data_order?order_id=<ID замовлення>&delivery_option_id=<ID способу доставки>
```

Перший — старий шлях `downloadEn`, коли перемикач нового друку вимкнений; код відкриває його через `window.open`. Цей старий шлях не викликали. Другий — читання початкових даних доставки; код використовує поле `data` відповіді. Запити другого маршруту з точними ID обох замовлень і `delivery_option_id=16954954` спостерігали серед ресурсів їхніх сторінок; тіло відповіді окремо не перевіряли. Це не підтверджує доступність маршрутів для всіх облікових записів.

## Реальна перевірка документів

Обидва PDF отримано через новий маршрут у вже авторизованому кабінеті Prom. На сторінці другого замовлення джерело Bigl було видиме в інтерфейсі.

| Замовлення | Джерело | `delivery_option_id` | ТТН у PDF | Розмір відповіді | Сторінки / фізичний розмір |
|---|---|---|---|---|---|
| `433580034` | Prom | `16954954` | `PRM-811362308` | 174 081 байт | 1 / приблизно 99,99 × 99,99 мм |
| `433455629` | Bigl | `16954954` | `201288134129` | 173 238 байт | 1 / приблизно 99,99 × 99,99 мм |

ТТН кожного документа перевірено на точний збіг. Візуальна перевірка обох PDF підтвердила правильні заголовок і ТТН, видимі штрихкоди та відсутність обрізання на сторінці формату 100 × 100 мм. PDF завантажено лише до користувацької папки Downloads; у Git вони не додані. Фізичного друку, створення або зміни накладних, замовлень чи чеків не виконувалось.

Спробу перевірити Prom API Bearer на маршруті кабінету зупинила автоматична перевірка дозволу **до виконання запиту**. Відповіді сервера на такий спосіб авторизації немає; стверджувати, що сервер його підтримує або відхиляє, не можна.

## Вимоги, враховані в інтеграції

- Потрібний окремий вхід у сесію Prom із прив'язкою до правильного магазину; перевірений результат не доводить, що достатньо поточного токена публічного API або логіна Rozetka Seller.
- Дозволяти лише потрібні запити читання до точного HTTPS-хоста `my.prom.ua` та перевірених шляхів. Не передавати сесію іншим хостам і не підмінювати нею ключ Rozetka Delivery.
- Перед прийняттям PDF перевіряти поточне замовлення, його спосіб доставки, точну ТТН у документі, тип і розмір відповіді, кількість сторінок та фактичний формат. Сторінку входу або JSON-помилку не приймати за накладну.
- Не викликати сусідні `create_declaration`, `save_created_declaration_number`, `return_package` чи інші операції зміни даних. Не копіювати сесійні секрети, PDF або дані покупців до Git та журналів.

Попередня перевірка підтвердила отримання існуючих накладних Prom і Bigl. Нова інтеграція використовує той самий маршрут і браузерну сесію, але живий вхід саме з CRMapp та фізичний друк потребують перевірки з користувацьким кабінетом. Автоматичні перевірки використовують синтетичні документи, ізольовані профілі та перехоплені відповіді; вони не надсилають завдань принтерам і не звертаються до справжніх замовлень. Багатомісні накладні поки відхиляються явно.

## Перевірки реалізації 16.10.2026

- Повний набір: 729/729 перевірок Development, включно з compiled XAML та попередніми сценаріями друку/зіставлення.
- Нові тести перевіряють ізоляцію магазинів, повторний вхід без дублювання підключень, збереження чернетки API-токена, числові/рядкові ID доставки, точний маршрут, відмову від HTML/JSON/ZIP/завеликого PDF, точну ТТН і односторінковий формат через справжній PDFium.
- Справжній WebView2 в ізольованому тимчасовому профілі отримує PDF із локально перехопленої відповіді. Перевірено 302 без переходу за Location, 401, паузу Retry-After 3600, блокування повторних запитів, скасування, перенесення браузера між фоновим HWND та вікном входу, відновлення профілю й синтетичного cookie без нового підключення.
- Початкова перевірка виявила, що WPF WebView2 не завершує ініціалізацію без батьківського HWND. Сесія тепер має невидимий HWND; час ініціалізації обмежено й скасування діє також під час запуску браузера. Проміжний дефект не встановлювався користувачу.
- Однофайловий EXE-кандидат скопійовано в іншу папку та запущено двічі: `PromCabinetBrowserVerified=true`, перевірки PDFium/XAML і повторного запуску успішні. Публікація виключає лише XML-документацію залежностей через стандартну властивість SDK; бібліотеки й нативний завантажувач WebView2 залишаються в EXE.
