# CRMapp — робоча версія

У версії 1.0.49 назва доставки Rozetka «Нова Пошта (поштомати)» розпізнається як Нова пошта. Виправлення працює і для вже збережених замовлень: їхні ТТН потрапляють до наявного джерела наклейок Нової пошти та до спільного друку чеків і наклейок.

У версії 1.0.48 кнопка «Друк наклейок і чеків» бере вибрані видимі замовлення з лівої таблиці. Наклейки та пов’язані чеки готуються повністю й підтверджуються разом, у поточному порядку замовлень. Сортування правої таблиці чеків не впливає на цей пакет. Приховані позначені замовлення не включаються. На різних принтерах пакети передаються паралельно; на одному — послідовно. Якщо один принтер не прийняв пакет, результат іншого зберігається й вибір залишається для перевірки; фізичний друк двох принтерів не є спільною транзакцією.

У версії 1.0.47 фільтр «Показувати скасовані» враховує групу статусів Rozetka Seller та відомі коди причин скасування зі старого кешу. Такі замовлення приховані за замовчуванням; після ввімкнення фільтра підсвічуються червоним і не потрапляють до автоматичного вибору для друку. Додаткових запитів до API немає. Точні та ручні історичні зв’язки з чеками зберігаються.

У версії 1.0.46 додатковий період перед «Дата від» за замовчуванням дорівнює 0 днів. Старе явно збережене значення можна змінити в «Налаштування → Маркетплейси → Додатково до “Дата від”, днів»; строк кешу залишається окремим параметром. Однакові облікові дані кількох підключень читають API один раз. Підтверджені UUID чеків Rozetka кешуються в пам’яті до зміни відповідних полів чи облікових даних; оновлення статусу, суми та ТТН продовжується. Фіскальна перевірка Checkbox охоплює потрібний період і пов’язані документи, зокрема старі оригінали повернень. Документи з уже відомим UUID перевіряють суперечливі коди й касу без повторного пошуку цього коду через API.

У версії 1.0.45 «Оновити все» та фоновий цикл запускають завантаження Checkbox, Prom, Rozetka й Нової пошти паралельно. Rozetka Delivery також має незалежний потік. Прив’язки обчислюються після завершення завантаження чеків; помилка однієї служби не зупиняє інші. Пізні результати після зміни дат, акаунта або конфігурації відхиляються. Під час підтвердженого друку фоновий результат чекає завершення передавання наклейок перед заміною рядків. Запити сторінок і магазинів усередині одного сервісу зберігають послідовність та обмеження частоти API. Загальний час залежить від найповільнішої служби та наступної перевірки деталей для прив’язок.

У версії 1.0.44 для чека, виданого через Rozetka, читається UUID із документованого PRRO-посилання та зіставляється з ID завантаженого Checkbox-чека. Якщо формат `link` не повернув підтвердженого посилання, для вже виданого документа з правом `prro_access` виконується один read-only запит `type=html`. Розпізнаються точні HTML-маршрути `api.checkbox.ua` та `api.checkbox.in.ua`; отримані URL не відкриваються. Точні ключі мають пріоритет над сумою й товарами; різний фіскальний код або контекст того самого документа дає конфлікт. Ручні прив’язки й відхилення збережені. Числовий ID замовлення Rozetka не прирівнюється до UUID або порядкового номера чека. Після запуску натисніть «Оновити все» для завантаження нових ключів.

У версії 1.0.43 галочка масового вибору та іконка кандидатів у заголовку таблиці замовлень працюють під час фонового оновлення маркетплейсів. Раніше загальна ознака зайнятості блокувала їх до завершення всіх запитів і деталей. Вибір застосовується до поточних видимих рядків; позначки зберігаються при оновленні тих самих замовлень. Друк наклейок і команда «Оновити все» зберігають блокування вибору. Пізнє читання історії після зміни акаунта, дат чи конфігурації не застосовує попередній вибір до нового контексту.

У версії 1.0.42 накладні Rozetka Delivery із замовлень Rozetka читаються через логін і пароль відповідного магазину Seller без окремого ключа Delivery. Потрібен доступ продавця до модуля доставки. Перед завантаженням PDF перевіряються основна RMP-ТТН і номер замовлення в цьому акаунті. Основна й документована партнерська ТТН одного документа друкуються один раз; історія зберігає обидва перевірені номери. Накладні Prom та незалежний список «Усі накладні» зберігають свої попередні підключення. Накладні не створюються і не змінюються; друк і далі потребує перегляду й підтвердження пакета.

У версії 1.0.41 повторні підключення Rozetka з однаковими збереженими логіном і паролем показують одне замовлення в таблиці. Для Prom збережено об’єднання за однаковим токеном. Об’єднання виконується тільки в поточному представленні: підключення, вихідні ключі кешу, ручні прив’язки й історія залишаються. Однаковий номер замовлення, назва магазину або логін з іншим паролем не об’єднують різні записи. Позначки друку з дублів переносяться до єдиного рядка; історія наклейок відновлюється за ТТН, як раніше.

У версії 1.0.40 налаштування Rozetka показують збережений логін після вибору підключення та відновлюють введені чернетки при перемиканні магазинів. Збережені пароль і токен залишаються прихованими; порожні поля залишають попередні значення. Індикатор «Збережено» не змінюється на чернетку через відображення збереженого логіна. Неповна нова пара логін/пароль відхиляється до запису секретів. Збереження блокує повторний запуск і редагування; налаштування маркетплейсів записуються до застосування фонового режиму й автозапуску. Після збереження підключення перечитуються для наступного оновлення без перезапуску CRMapp.

У версії 1.0.39 у заголовку таблиці замовлень та обох таблиць чеків є іконка фільтра з галочкою для вибору кандидатів на друк. Для замовлень вибираються видимі нескасовані записи з пов’язаним чеком, чиї наклейки ще не передавалися Windows; враховуються також збережені підтверджені зв’язки поза поточним списком чеків. Перед вибором перевіряється локальна історія наклейок: частково передані пакети й невідомий результат передавання виключаються. Для чеків вибираються ненадруковані завершені документи з пов’язаним нескасованим замовленням. Інші видимі галочки знімаються, приховані фільтрами зберігаються. Іконка лише змінює вибір; друк запускається звичайною кнопкою з попередньою перевіркою пакета.

У версії 1.0.38 є одна кнопка «Оновити все» (F5) на всіх вкладках: вона оновлює чеки Checkbox, замовлення маркетплейсів з автоприв’язками та накладні Нової пошти й Rozetka Delivery за вибраний період. Окремі кнопки оновлення чеків, замовлень, автоприв’язок і накладних прибрані. Збій або відсутні ключі одного сервісу не зупиняють інші; стан кожної служби доступний у підказці кнопки. Повторний запуск заблоковано до завершення, а зміна дат скасовує цикл. Явне оновлення не переривається переходом між вкладками. Під час друку оновлення недоступне; під час спільного оновлення друк не починається.

У версії 1.0.37 суми замовлень і чеків виділено жирним шрифтом. В обох таблицях чеків колонка «Сума» розташована одразу після часу, на попередньому місці «Тип чека»; «Тип чека» перенесено далі, після номера чека. Колір рядків, формат сум, виділення тексту й копіювання збережені.

У версії 1.0.36 верхній тулбар вкладки «Чеки та замовлення» розміщено в один горизонтальний рядок. Прибрано кнопки «Розширити на 30 днів» і «Скасувати підготовку» з цього тулбара. Перемикач автоматичного зіставлення має коротку назву «Автоприв’язка» з повним поясненням у підказці. У вузькому вікні доступна горизонтальна прокрутка тулбара.

У версії 1.0.35 скасовані замовлення при ввімкненому «Показувати скасовані» мають світло-червоний фон і темно-червоний текст. Цей колір має пріоритет над палітрою маркетплейсу й надрукованими наклейками та оновлюється після зміни статусу. За замовчуванням скасовані замовлення й далі приховані.

У версії 1.0.34 вибір усіх і зняття вибору перенесені у галочку заголовка першої колонки кожного дашборду. Перше натискання позначає видимі доступні рядки, повторне знімає всі галочки відповідної таблиці, включно з прихованими фільтром, як колишня кнопка «Зняти всі». Частковий вибір показано рискою; натискання доповнює його до всіх видимих. Чеки на двох вкладках, замовлення для наклейок та накладні мають незалежні перемикачі. Видалені накладні й замовлення без ТТН не входять у масовий вибір; скасовані залишаються під поточним фільтром. Окремі кнопки «Виділити всі»/«Зняти всі» та їхні аналоги для замовлень прибрані.

У версії 1.0.33 скасовані замовлення за замовчуванням приховані в таблиці замовлень. Перемикач «Показувати скасовані» повертає їх у поточний список із урахуванням пошуку, дат та інших фільтрів. Це лише фільтр відображення: дані, історія, галочки й наявні прив’язки зберігаються. На кожному новому запуску програми скасовані знову приховані.

У версії 1.0.32 на вкладці «Усі накладні» є окремі галочки, вибір усіх видимих, перегляд, друк позначених видимих накладних і історія передавання. Друк використовує збережений принтер наклейок та існуючий перегляд із підтвердженням; накладні не потребують замовлення чи чека. Усі місця й перевірені сторінки включаються в один Windows job. Приховані фільтром галочки не друкуються, після успішного передавання знімаються лише галочки переданих накладних. Видалені документи не можна позначати для друку. Раніше передані або невизначені документи вимагають явного підтвердження повтору в перегляді. Колонка «Пов’язані замовлення» показує точні відповідності ТТН серед завантажених замовлень, з урахуванням відомого акаунта; порожня колонка не означає, що замовлення не існує. Відображення цих відповідностей не змінює прив’язок чеків.

У версії 1.0.31 текст у клітинках усіх дашбордів можна виділяти мишкою й копіювати частинами: перетягування виділяє фрагмент, подвійний клік — слово, Ctrl+C або меню правої кнопки копіює тільки виділений текст. Значення залишаються доступними лише для читання. ТТН та номери замовлень із діями зберігають відкриття звичайним кліком; перетягування або подвійний клік не відкривають перегляд. Відкриття чека окремими кнопками й галочки друку працюють як раніше.

У версії 1.0.30 додано вкладку «Усі накладні». Вона читає документи безпосередньо з усіх налаштованих акаунтів Нової пошти та Rozetka Delivery за обидві вибрані дати, незалежно від замовлень, їхніх статусів чи прив’язок до чеків. Список завантажується при відкритті вкладки; новий період завантажується автоматично, кнопка «Оновити накладні» або F5 повторює запит. Є пошук, фільтр перевізника, сортування, виділення й копіювання клітинок. Архівні й видалені документи Rozetka Delivery включені та позначені у статусі. Наявність документів обмежується правами збережених акаунтів API; відсутній ключ чи помилка одного джерела показуються під таблицею та не приховують отримані документи інших джерел. Кнопки друку чеків на цій вкладці приховані.

У версії 1.0.29 кнопки налаштувань маркетплейсів і наклейок прибрані з панелі замовлень. Обидва розділи доступні через загальну кнопку «Налаштування». У таблицях можна виділяти клітинки та діапазони (Ctrl/Shift) й копіювати значення через Ctrl+C або меню правої кнопки → «Копіювати». Ctrl+A у таблиці виділяє всі клітинки для копіювання; це не ставить галочки друку. Кнопки «Виділити всі»/«Вибрати видимі для наклейок» і далі керують галочками друку.

Біля налаштувань підключення показано стан збережених ключів/облікових даних: зелений «Збережено», помаранчевий «Нове значення ще не збережено», сірий «Не налаштовано» або стан недоступний. Індикатори є для Checkbox, Prom, Rozetka, Нової пошти, Rozetka Delivery і підключення Seller для доставки. Порожнє поле пароля/ключа не означає, що збережених даних немає. Індикатор показує наявність локально збережених даних; перевірка API лишається окремою дією. Значення ключів і паролів не відображаються.

Сіре неактивне виділення більше не перекриває кольори чеків і замовлень після друку чи переходу фокуса. Вибраний рядок зберігається для ручної прив’язки; зелений колір надрукованих чеків і палітри Prom/Rozetka залишаються видимими. Активне виділення таблиці працює як раніше.

Номер у колонці «ТТН» клікабельний і відкриває перегляд наклейки саме цієї накладної. Окрема колонка «Етикетка» прибрана. Якщо накладних кілька, кожна має своє посилання; якщо ТТН немає, посилання не показується. Натискання номера не запускає друк і не змінює галочки вибору.

Таблиця замовлень компактніша: колонки «Маркетплейс», «Зв’язок із чеками», «Пов’язані чеки» й «Доставка» прибрані. Prom показано світло-синім, Rozetka — світло-зеленим; після передавання всіх ТТН замовлення в чергу друку відтінок стає насиченішим. Поруч із галочкою є номер рядка в поточному відфільтрованому й відсортованому списку. Кнопки чеків залишилися в «Відкрити чек», а статус, пояснення й список прив’язок доступні на інфоіконці ⓘ поруч із ними, зокрема для замовлень без чека.

Відсутність ключа доставки не зупиняє друк доступних наклейок. Відправлення без ключа пропускаються й показуються у перегляді пакета; їхні галочки залишаються, а історія не позначає їх надрукованими. Підтвердження друку стосується лише доступних наклейок. Якщо пропущено всі відправлення, завдання друку не створюється й повідомлення залишається у статусі без окремого блокувального вікна.

Пошук зв’язків використовує тільки замовлення та чеки без зв’язку й виключає скасовані замовлення. Вони залишаються в таблиці; ручні та точні фіскальні прив’язки зберігаються. Якщо скасовано замовлення зі збереженим ймовірним автозв’язком, цей автозв’язок знімається і чек знову доступний для пошуку.

Уже знайдені автоматичні пари активних замовлень зберігаються після оновлень і перезапуску; їхні товари не порівнюються повторно з новими документами. Старі нерозподілені групи однакових продажів також зіставляються, якщо повні товари та час документів залишають лише один можливий розподіл усієї групи: раніший чек не може належати пізнішому замовленню. Якщо можливих розподілів кілька або дані неповні, потрібен ручний вибір. Для зміни помилкової пари використовуйте ручне відв’язування або прив’язування.

## Запуск

1. Windows 10/11 x64. Потрібен **Microsoft .NET Desktop Runtime 8 x64**, не SDK, не ASP.NET і не .NET Framework 4.8.
2. Перевірка: `powershell -NoProfile -ExecutionPolicy Bypass -File .\Ensure-DesktopRuntime.ps1`.
   Якщо Runtime відсутній: та сама команда з `-Install`. Встановлення офіційного стабільного пакета WinGet потребує підтвердження; UAC підтверджуйте тільки для Microsoft Desktop Runtime. Автоматичного перезавантаження немає. За відсутності WinGet: [офіційний Microsoft Desktop Runtime 8](https://dotnet.microsoft.com/download/dotnet/8.0), Windows x64; перевірте цифровий підпис завантаженого інсталятора (Microsoft Corporation). Не обходьте попередження підпису.
3. Скопіюйте `app\CheckboxBatchPrinter.exe` у власну окрему папку та запускайте звичайним користувачем. Для роботи потрібен лише EXE і встановлений Desktop Runtime; сусідні службові скрипти необов’язкові. Права адміністратора для CRMapp не потрібні.

У «Налаштування → Діагностика» показано версію, канал Production, commit SHA та папку даних.
Назва головного вікна — **CRMapp — робоча версія**.

«Виділити всі» ставить галочки на всіх чеках поточного списку. «Зняти всі» знімає також приховані фільтром галочки активної вкладки. «Чеки за сьогодні» та «Сьогодні» одразу завантажують сьогоднішні чеки за часом Києва, скидаючи пошук і тип чека. Після успішного передавання на друк галочки переданих чеків знімаються; зелений колір та історія залишаються. Якщо сталася помилка або ви скасували друк, галочки зберігаються.

## Дані та початкове перенесення

Production використовує **`%LOCALAPPDATA%\CheckboxBatchPrinter-Production`**. Development залишається у `%LOCALAPPDATA%\CheckboxBatchPrinter`. Розташування EXE не впливає на ці шляхи. Це незалежні профілі без синхронізації.

Щоб перенести поточні налаштування, історію друку, ручні прив’язки, кеш та зашифровані облікові дані, **до першого звичайного запуску production**:

1. Закрийте всі екземпляри Checkbox Batch Printer/CRMapp.
2. Під тим самим Windows-користувачем запустіть:
   `powershell -NoProfile -ExecutionPolicy Bypass -File .\Copy-DevelopmentProfile.ps1`
3. Підтвердьте одноразове копіювання. Можна спочатку додати `-WhatIf` для перевірки без запису.

Джерело не змінюється. Спершу перевіряється доступність усіх DPAPI-файлів без виведення секретів; потім створюється окрема резервна копія `%LOCALAPPDATA%\CheckboxBatchPrinter-profile-backup-<id>` з доступом лише поточного користувача та SYSTEM. Production-копія також має захищені ACL. Існуючий production-профіль **не перезаписується**, навіть якщо порожній: зупиніться й окремо узгодьте перенесення. Не видаляйте свою історію заради повторного запуску скрипта. За помилки резервна копія/незавершена staging-папка зберігаються для перевірки, а не видаляються автоматично.

На іншому ПК/під іншим користувачем DPAPI-секрети не гарантовано доступні. Налаштуйте чистий production-профіль і введіть облікові дані локально. Не надсилайте резервні копії або папку даних у Git, ZIP програми чи чат.

Окремі дані **не ізолюють від реальних API та спільного принтера**. Не запускайте паралельні реальні завдання development/production. Фізичний друк перевіряється лише вами після явного погодження.

## Налаштування наклейок і Нової пошти

«Налаштування → Друк наклейок → Налаштувати друк наклейок і доставку»: виберіть принтер наклейок, його фізичний формат і кількість копій. Для Prom введіть **API-ключ Нової пошти** в одне поле й натисніть «Зберегти». Якщо магазинів кілька, спочатку виберіть потрібний магазин; якщо один — додаткових виборів акаунта/прив’язки немає. Порожнє поле залишає попередній ключ. Ключ зберігається захищено в чинному production-профілі, не в папці EXE.

Масштаб/зміщення/орієнтація, окремий токен Rozetka Delivery та Seller доступні у згорнутих «Розширених налаштуваннях». Окремого редактора NP-підключень більше немає: ключ вводиться тільки в основному полі для відповідного магазину. Збережені підключення та прив’язки не видаляються.

Для друку позначте потрібні замовлення галочками наклейок і натисніть «Друк наклейок». Програма завантажить один PDF вибраних ТТН кожного налаштованого NP-акаунта, без попереднього читання списку накладних. Усі сторінки розподіляться за номером ТТН, включно з кількома етикетками одного відправлення. Окремо відкривати налаштування для кожного замовлення не потрібно. Потім перегляньте всі етикетки й натисніть «Підтверджую — друк усього пакета». Відсутня ТТН, невпізнана/стороння сторінка, непідтримуваний формат або нестача сторінок для відомої кількості місць зупиняють пакет. Без даних про кількість місць програма включає всі отримані сторінки, але не стверджує, що їх повноту доведено.

«Перевірка накладної…» залишається необов’язковою окремою діагностикою. Це вікно лише читає актуальний збережений ключ магазину; полів ключа, акаунта, прив’язки, календарів і кнопки збереження в ньому немає. Лише ця діагностика читає останні 7 днів створення ТТН за Києвом; старіші ТТН за межами цього періоду в ній не знаходяться. Перевірка не запускає друк і не створює ТТН. Для звичайного друку відкривати її не потрібно.

Починаючи з 1.0.15, два або більше вибраних відправлень одного NP-акаунта потребують одного PDF-запиту. Фіксованої паузи 2 секунди немає. Якщо акаунти різні — потрібен окремий запит для кожного. Час підготовки залежить від відповіді НП; отримання за 2 секунди не гарантується. Після помилки програма не повторює цей запит автоматично.

Якщо Нова пошта обмежила частоту запитів, кнопка перевірки покаже зворотний відлік. Дочекайтеся його завершення й натисніть перевірку один раз: автоматичного повтору немає, а повторне відкриття вікна не скидає паузу. Ключ через це змінювати не потрібно. Лише після відповіді про обмеження діє серверний `Retry-After` або локальна пауза щонайменше 60 секунд. Це не гарантує, що серверний ліміт уже минув, особливо якщо цим акаунтом користуються інші програми.

## Оновлення

Закрийте CRMapp через значок у треї → «Вийти». У розпакованому production-комплекті запустіть:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\Update-Production.ps1
```

Типовий шлях встановлення — `D:\Portable Soft\CheckboxBatchPrinter.exe`; інший можна вказати через `-TargetExecutable "D:\Інша папка\CheckboxBatchPrinter.exe"`. Скрипт перевіряє production-канал і контрольні суми, створює захищену резервну копію старого EXE та всього профілю в `CheckboxBatchPrinter-backups` поруч із програмою, потім атомарно замінює EXE. Дані в LOCALAPPDATA залишаються незмінними, включно з історією чеків/ТТН, кешем, зв’язками та ключами. Пониження версії або оновлення відкритої програми зупиняється; повторне встановлення ідентичного EXE нічого не змінює. `-WhatIf` показує дію без запису. Запускайте під тим самим Windows-користувачем, що використовує CRMapp.

Якщо старий EXE видалено, та сама команда відновить його з готового production-пакета у наявну папку встановлення. Перед відновленням створюється резервна копія профілю; історія, налаштування й ключі не змінюються. Копії старого EXE у цьому випадку немає, бо він уже відсутній. Видаляти EXE для звичайного оновлення не потрібно.

У репозиторії `scripts\Update-Production.ps1` без параметрів вибирає останній готовий пакет з `artifacts\production`. Якщо версія коду новіша за готовий пакет, скрипт зупиняється з указаними версіями та інструкцією додати `-Build`, замість повідомлення, що стара версія вже актуальна. `-ReleaseDirectory "..."` встановлює конкретний розпакований комплект незалежно від версії коду; `-Build` спочатку збирає й перевіряє поточний закомічений Git HEAD, потім встановлює саме його пакет. `-WhatIf` для готового пакета працює також із відкритою CRMapp; для справжнього встановлення потрібно вийти з програми через трей. Немає автоматичного git pull, коміту, завершення процесу або запуску програми після оновлення.

`build-info.json` і `SHA256SUMS.txt` описують конкретний комплект. `SHA256SUMS.txt` містить SHA-256 усіх інших файлів комплекту, крім себе. Не переносіть .NET DLL із Program Files; вони завантажуються з установленого Runtime.
