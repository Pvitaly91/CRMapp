# Rozetka — лише ID чека; імовірне зіставлення — тільки Prom

Історичний звіт версії 1.0.64. У 1.0.65 користувач дозволив резервне зіставлення Rozetka за правилами Prom, коли фіскального ключа ще немає. [Чинна поведінка](ROZETKA_MATCHING_FALLBACK_REPORT.md).

Версія 1.0.64 застосовує явне правило користувача: Rozetka не бере участі в пошуку за сумою, товарами, кількістю, датою або способом оплати. Точна пара встановлюється за UUID чека Checkbox із документованого поля чи посилання. Якщо Seller надає фіскальний номер, авторизований точний пошук Checkbox може спочатку отримати UUID; до цього сам збіг номера з локальним чеком і номером каси не утворює точного зв’язку Rozetka.

## Що змінено

- Кандидати, товарний граф, підрахунок конкурентів, кількості й порівняння оплати для ймовірних пар включають лише замовлення Prom.
- Товарні деталі чеків не завантажуються для пошуку пари Rozetka за сумою.
- Збережені ймовірні пари Rozetka видаляються з робочого кешу при його читанні/використанні й не резервують замовлення чи чеки. Версія алгоритму знімків змінена, щоб старий граф не міг повернути таку пару. Схема захищеного файлу не змінюється; Prom-зв’язки читаються як раніше.
- Точні UUID-пари та явні ручні рішення збережені. Фіскальні суперечності, зміна касира, права доступу та колізії ID перевіряються як раніше.
- Сума товарів Rozetka й доставка показуються окремо; правильне відображення суми не використовується як доказ прив’язки.

## Межа автоматичного зв’язку

Замовлення Rozetka без фіскального ID залишається без автоматичної прив’язки, навіть коли ціна та повний кошик збігаються. Програма не заповнює ID із номера замовлення, суми або номера чека. Користувач може зберегти явне ручне рішення. Зміна правила не створює запитів PRRO іншого формату й не обходить чинні паузи після помилок.

## Перевірки

Регресійні сценарії охоплюють Rozetka з однаковою сумою й товарами без ID, старі ймовірні пари після читання кешу/оновлення, UUID та URL із UUID за різної суми, фіскальний номер до й після авторизованого отримання UUID, незмінну поведінку Prom, ручні рішення, колізії та збереження готових точних пар під час оновлення. Фізичний друк і зміна робочого профілю для перевірки алгоритму не потрібні.

Повний локальний набір: **680/680**. Окремо перевірено відсутність товарних запитів для Rozetka, видалення старих RZ-припущень без втрати Prom-пар і деталей, повторне відкриття та неповне оновлення, а також ID-зв’язок Rozetka за різних сум і назв товарів.
