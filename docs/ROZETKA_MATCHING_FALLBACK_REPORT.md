# Rozetka: ID чека з пріоритетом, зіставлення Prom за відсутності ключа

Версія 1.0.65 враховує затримку появи фіскальних ідентифікаторів у Seller API. Спочатку застосовуються ручні рішення й точні фіскальні ключі. Для замовлення Rozetka без ключа використовується той самий алгоритм ймовірного зіставлення, що для Prom: сума товарів без доставки, той самий календарний день у Києві, товари, кількість і відомий спосіб оплати. Неповне завантаження, суперечності й неоднозначні кандидати обробляються наявними перевірками алгоритму.

Ймовірна пара має стан Suggested і відповідне пояснення. Коли Seller надає UUID, фіскальний код чи посилання, збережене припущення більше не резервує замовлення. Фіскальний номер перевіряється через авторизований пошук Checkbox; точний UUID може підтвердити попередню пару або замінити її. Ключ, який уже є, але не підтверджений чи суперечить іншим даним, блокує резервне зіставлення. Ручні рішення мають звичний пріоритет.

Одна спільна політика застосовується до нових кандидатів, товарного графа, завантаження деталей, збережених зв’язків і відновлення кешу. Незмінні ймовірні пари зберігаються під час оновлення й повторного запуску. Стара версія графа інвалідується, щоб врахувати додані Rozetka-кандидати та конкуренцію між магазинами.

Запити PRRO залишаються `type=link` із чинними паузами після помилок. Резервне зіставлення не потребує нового запиту PRRO або іншого формату чека.

## Перевірки

Регресії охоплюють Rozetka без ключа, зокрема невказану валюту API й повний кошик; спільну конкуренцію Prom/Rozetka; збереження прийнятої пари в кеші, при F5 і повторному запуску; появу ID іншого чека після ймовірної пари; непідтверджені та суперечливі ключі; точний UUID при різних сумах; ручні рішення й відсутність фізичних завдань друку під час перевірок.

Окреме читання робочого профілю й деталей одного чека підтвердило результат на парі замовлення №908891418 / чек №4961: сума товарів 390 грн, доставка 49 грн окремо, фіскальний ключ відсутній, результат Suggested / AmountAndProducts. Перевірка врахувала 206 завантажених чеків і 1451 замовлення, виконувалася в пам’яті; жодного запису профілю або завдання друку не створено.

Повний локальний набір — **684/684**. У тесті налаштувань також усунено гонку очищення тимчасового каталогу: перевірка чекає завершення читання стану DPAPI перед видаленням тестових файлів. Робоча логіка збереження облікових даних не змінювалася.
