# Точний UUID чека Rozetka — 1.0.44

На робочій парі замовлення / чека зі скриншота користувача Seller повертає `prro_receipt_status=1`, провайдера `checkbox` і фіскальний код, що точно збігається з кодом завантаженого чека. `GET /prro/receipt/{order_id}?type=link` повертає HTTP 200 із `success=false`, кодом 15005, тоді як документовані `type=html` і `type=pdf` успішно повертають URL на `api.checkbox.in.ua`. Публічна документація не пояснює 15005, тому конкретна причина цієї серверної помилки не вгадується. HTML-посилання містить UUID саме завантаженого чека; PDF для прив’язки не потрібний і не завантажується.

Клієнт спершу зберігає попередній шлях `type=link`. Після неавторизаційної помилки, відсутнього або непідтвердженого посилання виконується один логічний запит `type=html` того самого замовлення й акаунта Seller. Відсутні права, невідомий/невиданий статус, остаточна 401/403, втрата прав після повторної авторизації та скасування не запускають цей fallback. Невдалий додатковий запит не видаляє замовлення, старий фіскальний доказ або безпечне посилання для відображення. Тип джерела фіксується правильно: `link` або `html`.

Парсер локально приймає лише HTTPS, точний `api.checkbox.ua` або `api.checkbox.in.ua`, стандартний порт і `/api/v1/receipts/{UUID}/html`. Збережено попередню підтримку 11-символьного фіскального ключа та лише документованих параметрів формату/організації. Інші домени, userinfo, фрагменти, перенаправлення, неоднозначні/невідомі параметри, закодовані чи нормалізовані шляхи не стають доказом. URL не відкривається; токен Checkbox нікуди не пересилається.

Офіційність старого домену підтверджена [специфікацією Checkbox](https://wiki.checkbox.ua/api) та [інструкцією інтеграції Gincore](https://wiki.checkbox.ua/integration/gincore). [Опис PRRO Seller](https://api-seller.rozetka.com.ua/apidoc/#api-PrroModule-GetPrroPrintReceipt) документує GET для `link/html/pdf`; [Checkbox OpenAPI](https://api.checkbox.ua/api/openapi.json) документує HTML-копію чека. Публічні OpenAPI старого й поточного доменів перевірені 11.10.2026: однакова версія 2.108.3+d569e323 і контракт HTML-маршруту.

Наявний matcher отримує типізований UUID і порівнює його з фактичним `ReceiptRecord.Id` поточного набору Checkbox. Сума та товари не потрібні для цього доказу. Фіскальний код/організація/каса того самого документа перевіряються на суперечність; кілька точних замовлень дають конфлікт. Ручне рішення має пріоритет, відхилення й заборона автоприв’язки не ігноруються. Bare fiscal code без контексту не стає точним зв’язком. Порядковий номер чека, зовнішній числовий ID Rozetka та внутрішній Checkbox `order_id` не ототожнюються.

Версію графа зіставлення змінено на v12, щоб не відтворювати висновки v11 для тепер розпізнаних URL. Окремі збережені автопари, ручні рішення, вихідні ключі підключень, історія чеків і наклейок залишаються. Доведені дублікати акаунта нормалізуються за попереднім правилом; фіскальні суперечності не відкидаються.

Реальна read-only перевірка новим `RozetkaOrdersClient` → локальним парсером → дедуплікацією → matcher підтвердила `Exact` для позначеної пари, нуль інших точних кандидатів, ідентичні UUID та фіскальний код. Усі HTTP-запити йшли лише до Seller, отриманий URL не відкривався. Дані робочого профілю та ручні рішення не записувалися; фізичний друк не запускався. Значення секретів і дані покупця не виводилися; конкретні ідентифікатори робочих документів не включені до репозиторію.

Додано сім регресій: реальні структури відповідей list/detail і помилка 15005 → HTML → UUID; пріоритет перед однаковою сумою й іншими товарами; обмежений fallback, права/повторна авторизація/скасування; URL-домени й маршрути; код/context-конфлікти, ручні рішення та повернення; дублікати Seller, загальне F5 й серіалізований перезапуск; відхилення, заборона автоприв’язки й скасовані кандидати друку. Старі графи v11 не відтворюються, але попередні окремі автопари зберігаються. Повний набір: **506/506**. Тести використовують вигадані дані й підмінений HTTP, без робочого API та фізичного друку.
