# Збереження прийнятих точних прив’язок — 1.0.66

У 1.0.65 ймовірні пари Suggested зберігалися окремо, а точні Exact — у сесії та загальних знімках алгоритму. Знімок залежав від результату авторизованого пошуку UUID. Цей результат навмисно не входить у серіалізацію сирих даних замовлення, тому після перезапуску знімок не відновлював пару без повторного пошуку. На робочому профілі це підтверджено для замовлення №908891682 і чека №4960: точна пара була в знімках, але не мала окремого стійкого запису. Ймовірна пара №908891418 / №4961 відновлювалася.

## Відновлення

Прийняті Exact-пари мають окремі обмежені записи в захищеному DPAPI-кеші: ключ замовлення, UUID і відбиток чека, відбиток сирих фіскальних даних, область увімкнених підключень та підтверджені посилання цього документа на UUID. Обліковий запис кешу ізольований. Довільні поля VerifiedReceiptId у сирому замовленні не стають збереженим доказом.

Після запуску локальний кеш відновлює тільки незмінні пари та перевіряє ручні рішення, суперечності й інші замовлення, що претендують на цей чек. Нове покриття API для вже прийнятої пари не потрібне. Зміна статусу перевезення, отримання нового знімка замовлення або недоступність API не видаляють незмінну прив’язку. Зміна фіскальних даних або чека потребує нової перевірки.

Раніше прийняті Exact із захищених знімків v17 переносяться тільки за точного відтворення збережених відбитків чека й замовлення. Перевірка ведеться окремо для кожного чека, тож інший період може мігрувати під час його відкриття. Обмежена історія спроб із тим самим строком кешу запобігає поверненню вже відхиленої пари зі старого знімка.

Прийнята прив’язка записується до тривалого завантаження товарних деталей; фінальне завершення оновлення також очікує збереження. Скасування наступного мережевого кроку не скасовує збереження вже прийнятого локального результату.

## Перевірки

Регресії охоплюють реальне DPAPI-збереження й новий екземпляр після перезапуску, відсутність повторної HTTP-перевірки незмінної пари, ручні рішення, зміну облікового запису та підключень, зміну фіскального ключа, конфлікти, скасування завантаження товарів і збереження ймовірних пар. Діагностика профілю виконується без записів і без фізичного друку.

На копії даних робочого профілю відновлено 42 прийняті точні пари, включно з №908891682 / чек №4960. Після серіалізації в пам’яті та створення нового сеансу всі 42 пари відновилися знову. API-запитів, записів робочого профілю та завдань друку не виконано.

Повний локальний набір — **692/692**. Окремо перевірено, що холодний запуск і повторне F5 не виконують нових запитів перевірки незмінних точних пар. Для нового єдиного фіскального ключа потрібна нова перевірка; суперечливі старий і новий ключі одного документа зберігають стан конфлікту.
