# Позначки друку в зовнішніх кабінетах — 1.0.51

Раніше колонка «Друк наклейки» показувала лише локальне передавання CRMapp у Windows. Тепер вона також враховує підтверджену позначку кабінету НП, отриману під час вже наявного оновлення списку накладних.

## Перевірені поля Нової пошти

12.10.2026 контрольне read-only читання `InternetDocument/getDocumentList` з чинного акаунта повернуло 61 накладну з `Printed:"1"` та рядком `DateLastPrint`. Виводилися лише назви, типи та значення цих службових полів; ключі, адреси, телефони, імена та дані накладних не записувались у репозиторій.

`Printed` читається як необов’язкова двійкова ознака: точні boolean true/false, число 1/0 або рядок "1"/"0". Відсутні, порожні та невідомі значення залишають стан невідомим. `DateLastPrint` зберігається як обмежений сирий текст без припущення про часовий пояс. Дата сама по собі, `ScanSheetPrinted` чи статус доставки не означають друку цієї накладної.

[Офіційна інструкція кабінету НП](https://my.novaposhta.ua/data/PersonalCabinet_User_Manual.pdf#page=65) пояснює, що «Друк PDF» відкриває форму для збереження або друку; [таблиця станів](https://my.novaposhta.ua/data/PersonalCabinet_User_Manual.pdf#page=93) окремо описує «роздруковано». Тому текст у CRMapp — «НП: позначено надрукованою», із датою та джерелом у підказці. Отримання форми може встановити позначку НП; вона не підтверджує фізичний вихід наклейки.

## Поведінка CRMapp

- Джерело з’єднується з конкретною ТТН через наявні перевірки перевізника, NP Ref та акаунта/його дозволених псевдонімів. Ознака не переноситься між іншими ТТН, документами чи магазинами.
- Зовнішні позначки зберігаються окремо від `LabelPrintAttempt`. Не створюються вигадані Windows job чи локальні успішні спроби. За наявності локального job його текст залишається основним, а зовнішня позначка доступна у підказці.
- Повністю позначені/передані наклейки отримують наявну підсвітку друку. Будь-яка позитивна позначка виключає замовлення з автоматичних кандидатів, щоб не передруковувати частину пакета. Ручні галочки доступні.
- У попередньому перегляді доступних сторінок показано окреме попередження про позначку кабінету. Зовнішній стан не видається за запис локальної історії. Нове позитивне свідчення після підтвердження потребує підготовки й підтвердження пакета заново.
- Відсутня/невідома ознака не стирає вже отриманий стан; явне false змінює лише позначку кабінету і не скасовує відомого локального передавання. Заміна ТТН, Ref, акаунта або налаштувань очищає непридатну проєкцію.
- Статуси чеків та фіскальні зв’язки не змінюються. Додаткового API-запиту для `Printed` немає: метадані вже містяться у списку накладних.

## Prom і Rozetka Delivery

Публічні схеми перевірені 12.10.2026:

- [Swagger Rozetka Delivery](https://rz-delivery.rozetka.ua/api/docs/) і [машиночитаний опис](https://rz-delivery.rozetka.ua/api/docs/swagger-ui-init.js): отримання label повертає PDF/base64, без прапорця, дати чи лічильника друку в моделях накладних.
- [Rozetka Seller](https://api-seller.rozetka.com.ua/apidoc/api_data.json): endpoint друку повертає файл, `need_label` означає потребу в додаткових стікерах. Контрольне читання чотирьох чинних накладних також не повернуло поля друку; виводилися тільки назви полів.
- [Prom DeliveryProvider](https://public-api.docs.prom.ua/documentation/Orders/schemas/DeliveryProvider.yaml): номер та `unified_status` описують доставку. Ознаки друку через кабінет немає.

Для цих джерел використовується достовірна локальна історія CRMapp; зовнішній друк залишається невідомим. Статус доставки чи завантаження PDF не підміняє його.

Регресії перевіряють API-формати та ізоляцію RD, точну публікацію маркера при порожньому трекінгу, відсутні/негативні дані, змішані локальні/зовнішні наклейки, відновлення рядків, кандидатів, повторні підтвердження, запізнілі маркери та відсутність вигаданих журналів чи історії чеків. Принтери під час перевірки не викликалися.
