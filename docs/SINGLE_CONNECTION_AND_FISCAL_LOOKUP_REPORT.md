# Збереження підключень і точна перевірка фіскального коду — 1.0.61

## Налаштування

Кнопки Prom і Rozetka тепер відкривають існуюче підключення цього сервісу. Перший запис створюється лише якщо такого підключення ще немає. Повторні натискання та заміна токена залишають той самий ID, чернетку ключа, історичні aliases, прив’язки й історію. Наявні різні магазини старих профілів не видаляються: вибраний магазин має пріоритет, при переході між сервісами вибирається увімкнений.

Ключ Нової пошти оновлює існуючий обліковий запис, зокрема коли ним користуються кілька прив’язаних магазинів. Новий магазин використовує єдине наявне NP-підключення. Якщо старих підключень кілька, а прив’язка відсутня, програма повідомляє про неоднозначність і не створює ще одну копію. Різні ключі в чернетках одного спільного підключення потрібно узгодити перед збереженням.

Checkbox і Rozetka Delivery уже використовували єдине місце збереження. Додано регресійні перевірки заміни пароля/токена, незмінного облікового контексту та історії, а також збереження порожніх полів.

## Чому не було зв’язку

Для перевіреного замовлення Rozetka повернула провайдера Checkbox і фіскальний номер, але не повернула UUID чека, організацію чи номер каси. Попередня перевірка вимагала контекст каси до пошуку; через це навіть наявний відповідний чек залишався без зв’язку. Порівняння суми не обходило непідтверджений фіскальний ключ.

Тепер джерело `prro.prro_receipt_fiscal_code` документа `rozetka.prro` від Checkbox дозволяє виконати точний авторизований запит:

`GET /api/v1/receipts/search?fiscal_code=...&self_receipts=true&limit=2&offset=0`

Джерело перевірене за [офіційним OpenAPI Checkbox](https://api.checkbox.ua/api/openapi.json), версія схеми під час перевірки `2.108.3+d569e323`. Доступ обмежений поточним касиром. Потрібні рівно один результат, незмінний фіскальний код з урахуванням регістру, непорожній UUID і збіг усіх відомих даних каси/організації. Невідоме джерело, інший провайдер, колізії, суперечливі ключі або ручне відхилення не створюють автоматичного зв’язку. Зміна касира скасовує результат.

Пошук не змінює фільтр дат дашборда і не додає сторонні чеки в таблицю. Схема Rozetka залишається token + `type=link`; резервних запитів PDF/HTML немає.

## Повторні запити

Кеш авторизованих відповідей існує лише в пам’яті та розділений за касирами. Однозначний результат зберігається 10 хвилин, порожній/неоднозначний — 5 хвилин. Повторні запити одного коду поєднуються. Помилка ключа кешується; помилки авторизації, мережі, 429 і сервера зупиняють перевірки інших кодів цього касира щонайменше на 5 хвилин, з урахуванням більшого Retry-After. Кеш обмежено 1024 записами; ліміт одного проходу — 100 кодів. Скасування не залишає часткової відповіді; вихід при зміні касира видаляє його тимчасові докази.

## Перевірка

15.10.2026 виконано один авторизований пошук Checkbox для пари зі скриншота. Авторизація й пошук дали HTTP 200; повернутий UUID збігся з уже завантаженим чеком, matcher повернув `Exact`. Повторна перевірка цієї пари не виконувала HTTP. Робочий профіль не змінювався, завдання друку не створювалися. У профілі підтверджено по одному підключенню Prom і Rozetka. Секрети, персональні дані та відповіді API не додані до репозиторію.

Автоматичні сценарії охоплюють реальні WPF поля збереження й повторне відкриття, ротацію спільного NP-ключа, збереження історії, ланцюг Seller → Checkbox → matcher, обидва шляхи оновлення дашборда, відмови/колізії/ручні рішення, кешування, cooldown, зміну касира та скасування під час очікування і після отримання відповіді. Повний локальний набір пройшов **652/652** перевірки; перевірка production-пакета повторює його для обох каналів. Результати випуску зазначаються в локальному `artifacts/RECOVERY_VERIFICATION.json`.
