## Реальні read-only перевірки: тільки Prom

У поточному профілі `C:\Users\admin\AppData\Local\CheckboxBatchPrinter\Marketplaces` знайдено налаштування й DPAPI-секрети. Вони прочитані через наявні `JsonMarketplaceSettingsStore` / `DpapiMarketplaceSecretStore`, без виведення значень. Перевірка процесів не знайшла запущеного `CheckboxBatchPrinter`, тому підтвердити шлях **фактично запущеного** EXE на момент перевірки неможливо. Код цієї ревізії й попередній tabs-білд використовують зазначений LocalAppData-каталог, незалежно від папки EXE.

Налаштовано дві увімкнені конфігурації Prom; повторне використання тих самих credentials у діагностиці не дублювало запити. Конфігурації не видалялися й не об’єднувалися. Однаковий магазин у двох різних ConnectionId може давати конфлікт при точному зіставленні — це окрема локальна перевірка налаштувань, не підстава автоматично видалити зв’язки.

Виконано рівно такі marketplace-запити:

| Запит | Обсяг | Результат |
| --- | --- | --- |
| `GET https://my.prom.ua/api/v1/orders/list?limit=5&sort_dir=desc` | 1 запит, 5 останніх замовлень | HTTP 200, `orders` — array |
| `GET https://my.prom.ua/api/v1/orders/{id}` | 3 різні ID з цього списку | Усі HTTP 200, `order` — object |

Всю отриману JSON-структуру переглянуто програмно в пам’яті; назовні виведено лише шляхи полів, JSON-типи й ознаки порожніх значень. У цих відповідях немає полів із receipt UUID, фіскальним номером або фіскальним URL. Є `id` (number), `date_created/date_modified` (string), `payment_data` (object/null), `delivery_provider_data` (object), `delivery_recipient` (object), товари й інші звичайні поля замовлення. URL товару та коментар не трактуються як фіскальний документ. Значення телефонів, адрес, токенів, паролів, повні відповіді, IDs реальних замовлень не збережені в Git/звіті.

**Важлива межа:** із цих відповідей неможливо підтвердити, що саме перевірені три замовлення вже мають видані через інтеграцію чеки. У користувача запитано 1–3 такі номери; на момент цієї перевірки конкретних номерів не отримано. Тому висновок стосується цих GET-відповідей і публічної схеми, а не доведеної відсутності будь-якого способу у всьому Prom.

У збережених налаштуваннях поточного профілю логін Checkbox порожній; захищений файл є, але цього недостатньо для авторизованого читання. Спроба через наявний authentication service завершилася локально до HTTP через відсутній логін; конкретний Checkbox-чек і його `context/order_id` **реально не перевірені**. Rozetka у профілі не налаштована. Після уточнення користувача «тестуй поки на пром» інші live API не викликалися. Не слід повторно просити секрети в чат: будь-яка майбутня авторизація — тільки локально у програмі.

## Актуальні офіційні контракти

- Prom: [OpenAPI index](https://public-api.docs.prom.ua/documentation/index.yaml), [GET details](https://public-api.docs.prom.ua/documentation/Orders/paths/GetOrder.yaml), [Order schema](https://public-api.docs.prom.ua/documentation/Orders/schemas/Order.yaml). Схема не містить фіскальних read-полів; у параметрах деталей немає документованого expand для них. В index немає окремого read-методу прикріпленого фіскального документа; є `POST /orders/{id}/attach_receipt`, але це **write**, він не викликався.
- Rozetka: [офіційна JSON-документація](https://api-seller.rozetka.com.ua/apidoc/api_data.json), [список](https://api-seller.rozetka.com.ua/apidoc/#api-Orders-GetOrderSearch), [деталі](https://api-seller.rozetka.com.ua/apidoc/#api-Orders-GetOrderDetails), [статус PRRO](https://api-seller.rozetka.com.ua/apidoc/#api-PrroModule-GetPrroReceiptStatus), [читання документа](https://api-seller.rozetka.com.ua/apidoc/#api-PrroModule-GetPrroPrintReceipt). `prro` документовано в list expand, але немає в актуальному detail expand. `prro_receipt_fiscal_code` описано як номер чека; `prro_receipt_service_name` — сервіс; це не UUID і не номер каси. При відсутньому статусі виконується лише GET `/prro/receipt-status/{order_id}`, а при status=1 — GET `/prro/receipt/{order_id}?type=link`. Ті самі кроки виконуються для нових замовлень поточного діапазону.
- Checkbox: [OpenAPI](https://api.checkbox.ua/api/openapi.json). `GET /api/v1/receipts/search` документує `fiscal_code` як фіскальний номер чека та `self_receipts`. HTML-route приймає UUID або 11-символьний код; параметри `simple`, `show_buttons`, `is_second_copy`, `organization_id`. Моделі чеків містять `organization_id`, `cash_register.fiscal_number` або повний `shift.cash_register.fiscal_number`.

## Що змінено

1. `FiscalDocumentReference` явно містить тип ключа, значення, джерело, OrderKey, провайдера, DocumentId, відомі organization/cash-register дані. `FiscalCode` зберігається окремим рядком з ordinal-порівнянням — регістр, символи й початкові нулі не втрачаються. Legacy `ReceiptIds` лишається сумісним, але новий реальний шлях не залежить від заповнення цього масиву.
2. Rozetka не втрачає list-only PRRO при відсутньому/null блоці деталей. Нові й старі замовлення отримують read-only URL. Помилка/відсутній дозвіл PRRO не губить саме замовлення і не оголошує, що чека немає.
3. При sync типізовані фіскальні докази з кешу об’єднуються з новими; різні твердження про той самий документ стають конфліктом, а не непомітною заміною. Стара схема кешу читається без видалення; нові поля додаються звичайним оновленням. Ручні рішення не переписуються.
4. URL розбирається **локально**, без переходу. Дозволено лише точний HTTPS host `api.checkbox.ua`, стандартний порт і шлях `/api/v1/receipts/{key}/html`. Для UUID перевіряється відповідність ID реально завантаженого Checkbox-чека. Для коду без UUID потрібен контекст. Query не заборонено цілком: підтримані документовані boolean-параметри форматування та UUID `organization_id`. Невідомі query/redirect, userinfo, fragment, підміна домену/шляху не є доказом. Інші формати, зокрема short URL `check.checkbox.ua`, ще не верифіковані й **не вгадуються**.
5. Фіскальний код із organization context перевіряється точним Checkbox read-запитом `fiscal_code=...&self_receipts=true&limit=2&offset=0`, без обмеження календарем і без зміни прав. Потрібна рівно одна відповідь, та сама організація й код. Каса, якщо відома, також повинна збігатися. Два результати не вважаються унікальним збігом. За один sync — до 100 різних таких пошуків із дедуплікацією. Доказ авторизованої перевірки існує лише в пам’яті й прив’язаний до облікового контексту; не довіряється після перезапуску/зміни касира.
6. Код із достовірно відомою касою може зіставлятися в поточному наборі лише при єдиному точному збігу code+cash register. Реальний Rozetka adapter **не вигадує касу** з OrderId чи ConnectionId. Bare fiscal code, невідомий провайдер або тільки назва магазину недостатні. Якщо API дає тільки такий код, автоматичний зв’язок залишається непідтвердженим.
7. Кілька документів одного замовлення зберігаються окремими DocumentId. Суперечність UUID/коду всередині одного документа — конфлікт. Продаж не підміняє повернення; працює власний точний ключ повернення або доведений ланцюг `related_receipt_id`. Ручне рішення пріоритетне, відхилення не перезаписуються.
8. Після sync повторне зіставлення оновлює marketplace/order/buyer/TTN уже завантажених рядків. Підстава автоматичного зв’язку показується явно. Лічильники пояснюють отримані замовлення та непідтверджені ключі, не заявляючи «чека не існує». «Усі чеки» не залежить від цієї перевірки й продовжує друкувати без зв’язку.

**Не підтверджено live:** фактичний формат Rozetka PRRO URL/провайдера конкретного магазину, code/organization із його відповіді, реальне зіставлення з Checkbox. Підтримка документованої структури й безпечні переходи перевіряються synthetic API-тестами; це не заміна live-прийманню.

## Тести й збірка

Розширено набір зі збереженням попередніх 78 сценаріїв. Нові перевірки проходять через `RozetkaOrdersClient` і HTTP transport до matcher/verifier, не лише через вручну створений `ReceiptIds`: URL нового замовлення; missing/null detail PRRO; збереження на повторному sync; конфлікти; формат URL і заборонені host/query; code+organization → Checkbox lookup → match; відмова, порожній результат і неоднозначність; інша каса/serial; кілька чеків і повернення; ручні рішення; серіалізація без runtime-підтвердження; відсутність фіскального ключа Prom. STA-сценарій перевіряє автоматичне заповнення рядка без ручного діалогу, F5 та незалежний fake-друк іншого чека. Фінальні результати й шлях збірки наведено у [загальному звіті](MARKETPLACE_ORDERS_REPORT.md).

## Запит до підтримки Prom — підготовлено, НЕ надіслано

> Вітаю! У замовленнях нашого магазину чеки вже видано через вбудовану інтеграцію Checkbox. Який read-only метод публічного API повертає для конкретного order ID UUID чека Checkbox, його fiscal_code або URL уже виданого фіскального документа? У GET /orders/list та GET /orders/{id} цих полів не бачимо. Чи потрібне додаткове право токена, параметр/розширення відповіді або окремий endpoint? Потрібні також правила для кількох чеків і повернень. Метод attach_receipt не підходить: змінювати замовлення не потрібно.

Номери прикладів користувач може додати до приватного звернення сам. Токен/пароль, чеки й персональні дані покупців не додавати. Запит не відправлявся автоматично.
