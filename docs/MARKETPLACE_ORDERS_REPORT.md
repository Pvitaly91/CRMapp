Робоча гілка: `codex/checkbox-marketplace-orders`. Незакомічених змін у використаній копії перед роботою не було; інші копії репозиторію не перезаписувалися.

## Реалізовано

- Реальні окремі адаптери Prom та Rozetka: авторизація, перевірка підключення, списки й деталі, документована пагінація, nullable-поля, decimal-суми, cancellation та часткові результати.
- Для Prom — Bearer API-токен; для Rozetka — логін/пароль, `POST /sites`, потім Bearer. Відмова авторизації не виводить секрети або сирі відповіді.
- Явний allowlist офіційних HTTPS host/path/method. Redirect вимкнений; відповіді обмежено 16 MiB, включно без Content-Length. Retry-After не скорочується, очікування можна скасувати.
- Окремий розділ «Маркетплейси», кілька підключень із постійними GUID, окремі секрети DPAPI. Для іншого Rozetka-логіна потрібне нове підключення; ротація пароля/токена того самого магазину зберігає його ID.
- Кеш із TTL 1–90 днів та довготривалі прив’язки/відмови — різні зашифровані DPAPI-файли в LocalAppData. Принтер, пароль Checkbox та наявна історія друку не мігруються й не видаляються.
- Нормалізований ключ `Marketplace + ConnectionId + OrderId`; покупець і отримувач окремі, товари/SKU/кількість/ціни, оплата, доставка/ТТН, вихідні значення статусу/дати/нерозпізнаної суми.
- Колонки маркетплейсу, номера замовлення та стану зв’язку; покупець/статус/ТТН вмикаються додатковим прапорцем. Нижній розгортний блок деталей, копіювання номера/ТТН, пошук і фільтри.
- Діалог ручної прив’язки: фільтри платформи/магазину, пошук номера/покупця/телефону/ТТН, порівняння чека і замовлення, явне підтвердження, відхилення кандидата, зміна й відв’язування. Кандидати не заповнюють підтверджені колонки.
- За замовчуванням історія замовлень починається за 30 днів до дати чеків; запас налаштовується й розширюється кнопкою. Старі відомі ID оновлюються окремо від поточного діапазону. Upsert без дублів; safety limit 1000 сторінок / 500 додаткових старих замовлень дає неповний результат.
- Синхронізація не займає стан друку MainViewModel, не змінює галочки чи вже сформований пакет. Помилки маркетплейсу не блокують перегляд/друк доступних чеків. F5 зберігає вибір у межах того самого касира. Зміна касира прибирає старі відомості маркетплейсу навіть після «Перевірити підключення → Скасувати».

## Контракти і точність зв’язків

Джерела та маппінги: [MARKETPLACE_API_CONTRACT.md](MARKETPLACE_API_CONTRACT.md), [Prom](PROM_CONTRACT_NOTES.md), [Rozetka](ROZETKA_CONTRACT_NOTES.md).

Prom GET Order не документує receipt UUID. Rozetka має фіскальний номер і опціональний PRRO URL, але не гарантує Checkbox UUID або його формат у URL. Checkbox `order_id` є UUID без документованого відповідника numeric marketplace ID; `context` не визначає ключі зовнішніх інтеграцій. Тому чинні адаптери не вигадують receipt UUID і не обіцяють автоматичної прив’язки кожного реального замовлення.

Matcher виконує точний зв’язок лише при однозначному перевіреному UUID; його переходи перевірено синтетичними довіреними даними. Для поточних Prom/Rozetka основний сценарій — кандидат за сумою/попередньою датою з явним ручним підтвердженням або ручний пошук. Навіть один кандидат не стає точним зв’язком. За невідомої валюти UI окремо вказує, що числовий збіг суми слабкий.

Ручна прив’язка має пріоритет і не перезаписується оновленням. Відхилений кандидат не відновлюється автоматично. Кілька чеків можуть належати одному замовленню. Для повернення використовується лише перевірений `related_receipt_id` і точний/підтверджений зв’язок початкового чека; підбір лише за сумою вимкнений. Суперечливі точні ключі показуються як конфлікт.

`self_receipts=true` збережено. API описує це як показ лише власних чеків. Наявність замовлення не дає доступу до чеків іншого касира і не доводить відсутність фіскалізації.

Формат URL замовлення в кабінеті не підтверджений офіційним контрактом — посилання не вигадано. Суми замовлення та чека показуються окремо; текст, QR і PNG фіскального чека не змінюються.

Послідовність локальної перевірки користувачем, окремо для **кожного** магазину:

1. Запустити новий EXE. «Налаштування → Маркетплейси → Додати Prom / Додати Rozetka», увімкнути підключення. Токен або логін/пароль вводити **тільки у програмі**, натиснути «Перевірити підключення», зберегти. Не надсилати секрети чи сирі API-відповіді в чат.
2. Обрати невеликий період чеків, перевірити налаштований запас історії замовлень; натиснути «Оновити замовлення». Звіряти кабінет із **показаним діапазоном замовлень (Київ)**, а не лише датами чеків. У кабінеті виставити ідентичні дати/статуси та інші фільтри.
3. Переконатися, що статус повідомляє про всі сторінки, а не часткове завантаження. Для перевірки пагінації потрібен період із більш ніж однією сторінкою: звірити загальну кількість та наявність замовлень із останньої сторінки. Таблиця чеків не є лічильником усіх замовлень; список замовлень доступний у діалозі прив’язки. Звертати увагу на раніше кешовані/поновлені старі замовлення — порівнювати лише однакову вибірку, а не весь кеш.
4. Для кількох відомих замовлень звірити номер, суму/валюту, покупця, **окремого отримувача**, товари/кількість/ціну та ТТН, відкрити деталі. Відсутнє в API поле має залишатися невідомим, не здогадкою.
5. Вручну прив’язати відоме замовлення до правильного чека; перевірити F5 → інші дати → повернення → закрити/відкрити програму. Перевірити пошук номера замовлення й ТТН. Окремо відв’язати, відхилити неправильного кандидата і переконатися, що він не повернувся після оновлення.
6. Під час достатньо довгої синхронізації натиснути «Скасувати оновлення» й перевірити повідомлення про неповну перевірку. Реальну помилку посеред пагінації/обмеження прав, якщо вони не виникли, залишити неперевіреними: не змінювати мережу чи серверні дані заради тесту. Автоматичні тести ці випадки покривають.
7. Для фіскальних ключів записувати лише **назви полів і висновок**, без значень/посилань із персональними даними. У поточному адаптері Rozetka кандидатами для дослідження є `prro.prro_receipt_fiscal_code` та `content.url` відповіді read-only `/prro/receipt/{id}?type=link`; їх фактична наявність у користувача не перевірена. Prom receipt UUID не припускаємо. Формат, семантику та однозначність із Checkbox потрібно довести окремо.

Обидва адаптери й надалі повертають `ReceiptIds = []`. Нової автоприв’язки за URL, фіскальним номером, UUID-здогадкою, сумою, телефоном, датою або товаром не додано. API створення/редагування чеків, замовлень, ТТН, статусів, повернень чи документів не викликалися.

### Алгоритм, який не видає припущення за фіскальний доказ

1. Зберігається пріоритет ручних рішень і точних UUID/URL/fiscal-code зв’язків. Суперечність або непідтверджений фіскальний ключ не обходяться через товари.
2. Лише `SELL/DONE`, повний набір товарів з обох API, однакова числова загальна сума, замовлення від 0 до 30 днів перед чеком. Для назв нормалізуються лише Unicode-композиція, регістр і пробіли; не використовується fuzzy/переклад/часткові слова. SKU різних систем не вважається гарантованим спільним ключем.
3. Порівнюються **всі** рядки з повтореннями: назва, кількість, ціна та сума. Перевіряється `quantity × unit_price = line_total`, сума рядків = загальна сума. Checkbox копійки/тисячні переводяться відповідно до контракту; дані Prom вже у звичайних грошових/товарних одиницях. Доставка не вилучається з кошика довільно: використовуються саме `Order.price` та всі повернуті товари.
4. Вимагається взаємна однозначність серед завантажених замовлень **і** чеків. Два однакові кошики, невідомі дати/суми або неповні потенційні конкуренти блокують припущення. Відхилення одного кандидата не доводить іншого.
5. Непорожні Checkbox root/line discounts, mixed `is_return`, передоплата, округлення, неузгоджений/відсутній total, malformed goods, неповні Prom/Rozetka products і непорожні відомі discount markers не використовуються для товарного автозв’язку. Ручне порівняння доступне. Старий кеш без нового `ItemsComplete` не вважається доказом повноти — потрібне звичайне оновлення, не видалення.
6. Результат — новий стан `Suggested`: **«Ймовірно: за товарами»**, замовлення/покупець/ТТН показуються, але жодне ручне рішення не записується. Для Prom валюта часто не надана — це явно вказано; відома не-UAH валюта блокує припущення. Це не доказ належності документа навіть при єдиному збігу: `self_receipts=true`, календар і доступ магазину обмежують видимий набір. Підтвердження/відхилення — локальні явні дії користувача.
7. Після явного sync для потенційних товарних пар автоматично читаються деталі Checkbox (тільки GET, до 100 за операцію). Кнопка «Зіставити за товарами» продовжує; ще не перевірені ID пріоритетні навіть після 100 помилок. Невдале читання лишається невідомим, не успішним порожнім кошиком. Скасування/зміна касира не дозволяють старій відповіді потрапити в новий контекст. Деталі й ймовірні зв’язки лише в пам’яті.

Реальний Prom GET для окремого замовлення з підтвердженим користувачем «Чек виданий» та його запис у list отримали HTTP 200, але не фіскальний ключ; [доповнений звіт](FISCAL_LINK_REPORT.md). У цьому етапі коду не було нових live API-запитів, фіскальних операцій або фізичного друку.
