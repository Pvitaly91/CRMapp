# Інтеграція замовлень маркетплейсів

Дата: 2026-09-23. База: актуальний GitHub `main b08e5ec82eb674496c8e0471e61423df521989e5`.
Робоча гілка: `codex/checkbox-marketplace-orders`. Незакомічених змін у використаній копії перед роботою не було; інші копії репозиторію не перезаписувалися.

## Реалізовано

- Реальні окремі адаптери Prom та Rozetka: авторизація, перевірка підключення, списки й деталі, документована пагінація, nullable-поля, decimal-суми, cancellation та часткові результати.
- Для Prom — Bearer API-токен; для Rozetka — логін/пароль, `POST /sites`, потім Bearer. Відмова авторизації не виводить секрети або сирі відповіді.
- Явний allowlist офіційних HTTPS host/path/method. Redirect вимкнений; відповіді обмежено 16 MiB, включно без Content-Length. Retry-After не скорочується, очікування можна скасувати.
- Окремий розділ «Маркетплейси», кілька підключень із постійними GUID, окремі секрети DPAPI. Для іншого Rozetka-логіна потрібне нове підключення; ротація пароля/токена того самого магазину зберігає його ID.
- Кеш із TTL 1–90 днів та довготривалі прив’язки/відмови — різні зашифровані DPAPI-файли в LocalAppData. Принтер, пароль Checkbox та наявна історія друку не мігруються й не видаляються.
- Нормалізований ключ `Marketplace + ConnectionId + OrderId`; покупець і отримувач окремі, товари/SKU/кількість/ціни, оплата, доставка/ТТН, вихідні значення статусу/дати/нерозпізнаної суми.
- Колонки маркетплейсу, номера замовлення та стану зв’язку; покупець/статус/ТТН вмикаються додатковим прапорцем. Нижній розгортний блок деталей, копіювання номера/ТТН, пошук і фільтри.
- Діалог ручної прив’язки: фільтри платформи/магазину, пошук номера/покупця/телефону/ТТН, порівняння чека і замовлення, явне підтвердження, відхилення кандидата, зміна й відв’язування. Кандидати не заповнюють підтверджені колонки.
- За замовчуванням історія замовлень починається за 30 днів до дати чеків; запас налаштовується й розширюється кнопкою. Старі відомі ID оновлюються окремо від поточного діапазону. Upsert без дублів; safety limit 1000 сторінок / 500 додаткових старих замовлень дає неповний результат.
- Синхронізація не займає стан друку MainViewModel, не змінює галочки чи вже сформований пакет. Помилки маркетплейсу не блокують перегляд/друк доступних чеків. F5 зберігає вибір у межах того самого касира. Зміна касира прибирає старі відомості маркетплейсу навіть після «Перевірити підключення → Скасувати».

## Контракти і точність зв’язків

Джерела та маппінги: [MARKETPLACE_API_CONTRACT.md](MARKETPLACE_API_CONTRACT.md), [Prom](PROM_CONTRACT_NOTES.md), [Rozetka](ROZETKA_CONTRACT_NOTES.md).

Prom GET Order не документує receipt UUID. Rozetka має фіскальний номер і опціональний PRRO URL, але не гарантує Checkbox UUID або його формат у URL. Checkbox `order_id` є UUID без документованого відповідника numeric marketplace ID; `context` не визначає ключі зовнішніх інтеграцій. Тому чинні адаптери не вигадують receipt UUID і не обіцяють автоматичної прив’язки кожного реального замовлення.

Matcher виконує точний зв’язок лише при однозначному перевіреному UUID; його переходи перевірено синтетичними довіреними даними. Для поточних Prom/Rozetka основний сценарій — кандидат за сумою/попередньою датою з явним ручним підтвердженням або ручний пошук. Навіть один кандидат не стає точним зв’язком. За невідомої валюти UI окремо вказує, що числовий збіг суми слабкий.

Ручна прив’язка має пріоритет і не перезаписується оновленням. Відхилений кандидат не відновлюється автоматично. Кілька чеків можуть належати одному замовленню. Для повернення використовується лише перевірений `related_receipt_id` і точний/підтверджений зв’язок початкового чека; підбір лише за сумою вимкнений. Суперечливі точні ключі показуються як конфлікт.

`self_receipts=true` збережено. API описує це як показ лише власних чеків. Наявність замовлення не дає доступу до чеків іншого касира і не доводить відсутність фіскалізації.

Формат URL замовлення в кабінеті не підтверджений офіційним контрактом — посилання не вигадано. Суми замовлення та чека показуються окремо; текст, QR і PNG фіскального чека не змінюються.

Portable-білд: `D:\Portable Soft\POS\CRMapp\artifacts\win-x64-marketplace-orders\CheckboxBatchPrinter.exe`; артефакти не входять до Git.

Перевірено реальні переходи ViewModel: друк під час синхронізації, незмінний пакет/галочки/історія, ручний зв’язок після F5 та створення нових ViewModel, недоступний API, зміна касира після Cancel, запізніла відповідь деталей, пошкоджені локальні налаштування, незмінність ID магазину Rozetka. Це не замінює перевірку всього інтерфейсу користувачем із реальними даними.

Автоматичні тести не користуються реальними секретами або покупцями. Перевіряють повну пагінацію/помилку посеред сканування, нульові поля, неоднозначні суми/дати, конфлікти, повернення, ручне збереження/відмову, ізоляцію, expiry/DPAPI, bounded retry, cancellation, заборонені write-запити, upsert старих статусів, незмінність вибору та порядку пачки під час синхронізації.

Реально виконані мережеві read-only операції в межах роботи: читання публічних офіційних OpenAPI/API-документів Prom, Rozetka та Checkbox. Викликів API приватних магазинів із реальними обліковими даними не виконано. Записів у Checkbox/Prom/Rozetka, нових чеків/замовлень, ТТН, повідомлень і фіскалізації не було.

## Що перевіряється локально з власними даними

1. Підключення продавців та наявні права читання; діапазон і кількість сторінок на реальному магазині.
2. Формат реальних monetary strings Prom, межа last_id; локальні приклади Rozetka timezone, набори expansions та наявність доступу PRRO. Документовані невизначеності не підмінені припущеннями про точні ключі.
3. Ручне зіставлення кількох відомих продажів/повернень, F5, зміна дат, перезапуск, повторне відкриття нового portable-білду.
4. Фізичний друк через установлений Windows-драйвер: папір, QR, довжина пачки, розділювачі. Новий модуль не змінює WindowsPrintService. Фізичний друк цієї версії під час роботи не виконувався і успішним не оголошується.

В основі `main b08e5ec` збережено наявний `printed-receipts.json` і підтвердження запуску друку. Ця інтеграція не переносить окремі гарантії інших reliability-гілок, відсутні у взятому main, та не прирівнює API-тести до підтвердження паперового друку.
