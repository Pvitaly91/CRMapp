# Накладні Rozetka Delivery через Seller — 1.0.42

Для замовлень Rozetka програма використовує збережені логін і пароль саме того магазину, якому належить замовлення. Окремий кабінет чи ключ Rozetka Delivery не потрібний. Акаунт має надавати право `module_octopus`; відмова у доступі не підмінюється переходом до іншого магазину. Налаштування Seller для Нової пошти не керує цим джерелом.

Контракт перевірено за [офіційною документацією Seller](https://api-seller.rozetka.com.ua/apidoc/api_data.json): авторизація `POST /sites`, список наявних документів `GET /delivery-rozetka/ttn-list`, PDF-копія `POST /delivery-rozetka/ttn-print-batch`. Перед PDF перевіряються повнота сторінок списку, точний номер замовлення та однозначна основна RMP-ТТН. На друк передається один основний номер; поле `carrier_track_num` підтверджує партнерський номер. `ext_id`, назва магазину чи однакова сума не замінюють цієї перевірки. Створення й редагування накладних виключені зі списку дозволених запитів.

Основна та перевірена партнерська ТТН одного замовлення використовують одну PDF-копію в поточній підготовці. Пакет зберігає всі її сторінки й друкує їх один раз. Захищена історія фіксує обидва перевірені номери та ключ замовлення/акаунта, тому після перезапуску рядок показує надруковану наклейку і виключається з кандидатів. Інший магазин з таким самим номером не успадковує цей стан; доведені підключення-дублі нормалізуються тим самим правилом, що й замовлення. Початкові замовлення, підключення й старі записи історії не переписуються; старі записи без ключа залишають попередню поведінку.

Наявний прямий Delivery API залишається для його окремого акаунта, замовлень Prom і вкладки «Усі накладні». Ця зміна не робить накладні Prom доступними в акаунті Seller і не додає незалежне перерахування накладних Seller до цієї вкладки.

Форма PDF зберігає фактичний розмір та всі сторінки. API не документує параметр формату, тому програма не вигадує його й не обрізає A4. Перевірка області принтера й попередній перегляд пакета залишаються. Документи та їхні растри зберігаються тільки в пам’яті операції; секрети й вміст документів не потрапляють у журнал.

Локальна перевірка 11.10.2026 використала збережені Seller-дані для двох наявних замовлень без окремого Delivery-токена. Авторизація підтвердила `module_octopus`; список повернув точні RMP/замовлення і повні метадані. Метод друку повернув `application/octet-stream`, тому цей тип допускається тільки для його точного маршруту після перевірки PDF. Документ із партнерською ТТН мав одну сторінку 99,99 × 99,99 мм, інший — одну сторінку 101,6 × 101,6 мм. PDFium перевірив та відрендерив усі сторінки; розміщення пройшло перевірку поточного драйвера й налаштувань принтера. Основна та партнерська ТТН отримали одну PDF-копію. Фізичний друк і запис історії в робочому профілі не запускалися; PDF/PNG на диск не записувалися.

Додано 13 автоматичних сценаріїв із підміненим HTTP: правильний магазин без Delivery-ключа, партнерські номери, відсутні/пошкоджені секрети, належність замовлення й неоднозначність, повна пагінація, права, JSON/PDF/MIME та перенаправлення, скасування, дозволені запити, збереження старих маршрутів, усі сторінки PDF, недостатня кількість місць/несумісний розмір, один документ для двох номерів та історія після DPAPI-перезапуску. Перевірено ізоляцію різних акаунтів і зміну канонічного підключення для доведених дублів. Повний набір: **496/496**. Скомпільоване вікно налаштувань відрендерено з поясненням Seller-джерела. Ці автоматичні сценарії не використовують робочі акаунти й фізичний принтер.
