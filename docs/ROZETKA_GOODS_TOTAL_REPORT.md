# Товари й доставка у сумі Rozetka — 1.0.63

Оновлення 1.0.64: сума товарів Rozetka залишається правильною для відображення. Автоматична прив’язка Rozetka за сумою й товарами вимкнена за новим правилом користувача; для неї потрібен ID чека. Зіставлення за комерційними ознаками залишається тільки для Prom. [Поточні правила](ROZETKA_ID_ONLY_MATCHING_REPORT.md).

## Причина

Раніше адаптер використовував `cost_with_discount` як `MarketplaceOrder.Total`. У Seller це сума замовлення разом із доставкою. Для товарного чека потрібна вартість товарів після знижки без доставки — `amount_with_discount`. Через різницю доставка могла блокувати навіть завантаження деталей відповідного чека: вибір кандидатів починається зі збігу суми.

Офіційні джерела: [OrderDetails](https://api-seller.rozetka.com.ua/apidoc/#api-Models-OrderDetails), [схема API](https://api-seller.rozetka.com.ua/apidoc/api_data.js). `amount` означає товари до знижки, `amount_with_discount` — товари після знижки; `cost` / `cost_with_discount` включають доставку.

## Реальна перевірка

15.10.2026 один read-only запит деталей замовлення зі скриншота повернув HTTP 200 і такі суми: `amount=390.00`, `amount_with_discount=390.00`, `cost=439.00`, `cost_with_discount=439.00`, `delivery.cost=49.00`. Єдина товарна позиція — 1 × 390 грн. Знижка дорівнює нулю; різниця 49 грн є доставкою.

Одним авторизованим читанням Checkbox отримано деталі відповідного чека: та сама позиція, кількість 1, сума 390 грн. Після підстановки підтвердженої суми товарів у модель у пам’яті matcher знайшов пару за сумою й товарами (`Suggested`, `Products=Match`) у повному наборі 204 чеків і 1449 замовлень, з чинними ручними рішеннями та збереженими розподілами. Профіль не змінювався, фізичного друку не було.

Фіскальні посилання цього замовлення в кеші відсутні, тому результат не позначається як точний UUID-зв’язок. Помилки PRRO `type=link` залишаються під наявною паузою; для виправлення сум додаткові запити PRRO не потрібні.

## Поведінка

Сума в таблиці та зіставленні відповідає явно наданій вартості товарів після знижки. Доставка зберігається окремо в `DeliveryCost`; знижка обчислюється лише з двох наданих товарних сум. Доставка не віднімається від чека й не перетворюється на знижку. Збережені фіскальні та ручні зв’язки мають пріоритет, невідома валюта не підміняється припущенням.

Перевірки охоплюють обидва способи отримання замовлень Seller, знижки, нульову вартість товарів, відсутні та некоректні поля, товари 390 + доставка 49 і конкурентний чек 439, а також випадок, коли лише сума з доставкою дорівнює сумі чека.

Повний локальний набір: **670/670** перевірок. Шлях API → адаптер → дашборд → завантаження товарів чека → matcher перевірено ізольовано для повного списку й для додаткового завантаження деталей. Ручні рішення та історія друку у цих сценаріях не змінюються.
