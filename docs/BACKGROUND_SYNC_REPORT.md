# Фоновий режим CRMapp — development 1.0.6

## Оновлення автоприв’язок у фоновому циклі (1.0.6)

Інформація про кількість зв’язків і перевірений діапазон після фонового циклу також описує recent-граф, а не неповне coverage ширшого історичного перегляду.

До виправлення новий наскрізний STA-тест через `BackgroundSyncCoordinator` → `MainViewModel` → workspace → таблиця завершився помилкою: очікувався `Suggested`, отримано `Incomplete` (**249/250**). Фон уже перевірив recent-вікно, але `visibleRecent` повторно зіставляв ті самі рядки з неповним coverage ширшого інтерактивного діапазону. Цей результат перекривав правильну recent-пару.

Фоновий цикл тепер обчислює один recent-граф за власним перевіреним coverage і застосовує його також до видимих recent-рядків. Календар, історичні рядки поза цим вікном, фільтри, вибір, ручні рішення та підтверджений пакет друку залишаються чинними. Алгоритм сум/товарів, API та друк не змінені.

Для нових ймовірних зв’язків потрібні успішне поточне читання Checkbox і повна відповідь усіх увімкнених маркетплейсів саме для recent-діапазону. Старий запис coverage не підміняє неповну нову відповідь. Відновлення з кешу recent-графа більше не залежить від можливості відновити ширший інтерактивний граф: збережені пари перевіряються проти поточних локальних документів; новий конкурент скасовує стару ймовірну однозначність.

Після виправлення **252/252** тести проходять. Додано перевірки: фоновий зв’язок при неповному ширшому interactive coverage без відкриття вкладки маркетплейсів; відновлення відомої пари після перезапуску та неповної відповіді API без автоприв’язки нової пари; повторний успішний цикл створює нову пару; прихований конкурент у наступному циклі знімає старий ймовірний зв’язок. Усі нові сценарії використовують синтетичні джерела та кеш із JSON-відновленням. Реальні нові документи через API та фізичний друк у цій перевірці не використовувалися.

## Виправлення після 7510f1e3

- Причина cooldown тепер типізована (`None`, `Transient`, `RateLimited`, `Authorization`), а не визначається за українським текстом статусу. Мережа/Resume дає одну негайну спробу лише після transient-помилки; одночасні події зливаються, а подія під час зайнятого іншого джерела виконується після нього. Повторний recovery у тому самому невдалому streak не породжує шквал запитів. Ручне «Оновити зараз» також може обійти transient, але не HTTP 429 `Retry-After` чи 401/403. Пауза в треї не стирає deadline. Авторизаційна пауза знімається тільки після явної успішної перевірки/збереження відповідних облікових даних.
- Для маркетплейсів HTTP 401/403 та останній HTTP 429 з `Retry-After` передаються до координатора як типізований стан; неповна вибірка й далі залишається неповною. Текст помилки не використовується для класифікації. Контракти зовнішніх API, read-only запити і алгоритм зіставлення не змінені.
- Інтерактивні `_from/_to` відокремлені від recent `BackgroundRange`. Фонове читання додає/оновлює рядки за ID та замовлення в кеші, але не змінює календар, історичну область графа, фільтри, виділення або ручні рішення. Покриття успішно прочитаних чеків і замовлень відстежується за діапазонами (обмежено 256 записами кожного типу). Фоновий matcher перераховує лише recent-групу; історична ймовірна пара не перераховується з вересневою областю. При переході на сьогодні вже завантажені рядки й замовлення показуються з кешу без відкладеного повторного читання Checkbox.

Контрольні сценарії: серпневий чек із ймовірним зв’язком, вересневе оновлення і повторне оновлення зміненого вересневого чека зберігають серпневий зв’язок; нове вересневе замовлення з’являється після переходу на відповідну дату. Окремий STA-тест підтверджує, що ручний зв’язок і вже підтверджений пакет друку не змінюються під час фонового циклу. Усі ці тести використовують підставні джерела й принтер, фізичного друку немає.

## Що зроблено

- Один `BackgroundSyncCoordinator` на процес: перший цикл після старту, далі 1/2/5/10 хвилин (типово 2); таймер, ручний запит і події повернення зі сну/появи мережі зливаються в одну операцію. Відсутня черга пропущених tick; підписки на системні події звільняються при виході. Checkbox і маркетплейси мають окремі результати; збій одного не скасовує інше.
- Робочий діапазон чеків — останні 7 днів за Europe/Kyiv (налаштовується 1–30). Замовлення читаються з відповідним чинним запасом історії для matcher. Це не поточний фільтр календаря. При зміні явно вибраного діапазону поза завантаженими чеками виконується окреме читання; фоновий діапазон залишається тим самим. Режим «Сьогодні» переходить на нову дату після опівночі Києва.
- Список чеків записується як DPAPI-захищений `receipts.dpapi`: обліковий контекст, межі завершеної вибірки, час успіху, схема, метадані й SHA-256 відбитки. Строк зберігання 30 днів, до 30 000 чеків/4 контекстів і обмеження розміру файлу. PNG, PDF, паролі й токени туди не записуються. Дані з кешу показуються перед мережею зі старим часом; при збої Checkbox показано «Дані станом на …; немає з’єднання». `orders.dpapi`, `automatic-matches.dpapi`, `receipt-order-links.dpapi` та історія друку залишилися окремими чинними сховищами.
- Рядки чеків оновлюються за ID; зберігаються їхні об’єкти, вибір у двох вкладках і стан друку. Повна успішна вибірка прибирає лише зниклі рядки в її діапазоні; інші відкриті історичні рядки залишаються. Змінений чек скидає застарілі деталі matcher. Для нових зв’язків повнота Checkbox та увімкнених маркетплейсів обов’язкова. Ручні рішення не переписуються фоновим кешем.
- Трей має відкриття подвійним кліком, меню «Оновити зараз», паузу/відновлення, налаштування й вихід. X приховує вікно, якщо прапорець трея ввімкнено; перше приховування показує коротке пояснення. Явний вихід скасовує worker, звільняє значок; при активному друці просить підтвердження. Параметр `--background` відкриває процес приховано. `--verify-package` обробляється до створення сервісів і worker.
- Один процес на Windows-користувача + канал + корінь даних. Другий EXE передає **лише** фіксований байт локальним named pipe поточного користувача, відкриває чинне вікно та отримує версію. Production і Development мають різні mutex, pipe, кеш і HKCU Run-імена. Автозапуск реєструється тільки через збереження відповідного прапорця; команда — фактичний шлях EXE в лапках + `--background`. Невідповідність шляху показується в налаштуваннях.

## Оновлення старих документів і межі API

Наявні клієнти Checkbox використовують пагінацію `receipts/search` за діапазоном дат; Prom — `orders/list` із UTC-датами й cursor `last_id`; Rozetka — `orders/search` із датами створення. Документований універсальний `updated_since` для цих трьох адаптерів не встановлено, тому worker перечитує **обмежене робоче вікно**, робить upsert за стабільними ID і не просуває стан успішної вибірки після неповної пагінації. Повторна повна сторінка Checkbox і межа 1000 сторінок тепер вважаються неповним результатом, а не успіхом. Відомі пов’язані замовлення поза вікном повторно запитуються за ID; обхід старих записів із лімітом 500 продовжується з локально збереженого курсора, щоб не застрягати на перших 500. Стан, ТТН і фіскальні поля перечитуються через ті ж read-only API. Деталі чеків кешуються чинним matcher; PNG/PDF фон не завантажує.

Після HTTP 429 враховується `Retry-After` Checkbox і маркетплейсів; коротші внутрішні повтори його не обрізають. Для тимчасових помилок координатор застосовує обмежений backoff, а 401/403 призупиняє відповідне джерело до явної повторної перевірки/збереження credentials. Стан кожного підключення Prom/Rozetka вже показується в інформації маркетплейсів; загальний рядок фону показує Checkbox і маркетплейси окремо.

## Перевірки

Локально виконано синтетичні регресії (fake API/printer), включно з керованим часом, злиттям таймера/F5, DPAPI-відновленням іншого контексту, upsert без втрати позначок і стану друку, локальною активацією другого екземпляра та створенням/звільненням tray icon на STA. Додано A/B/C і coalescing під час зайнятого циклу; D/E/H перевірено наскрізно через `MainViewModel`/workspace/таблиці; F/G — через ручний зв’язок та frozen print batch. Типізований 401/429 маркетплейсу перевірено до кешу. Весь набір після змін: **249/249** тестів. Окремий self-contained win-x64 Development 1.0.4 перевірено ізольованим `--verify-package`; він не використовує реальний профіль, мережу або принтер. Жоден із цих тестів не виконує фіскальні операції чи фізичний друк.

## Що не перевірено / залишкові обмеження

- Реальні підключення Checkbox, Prom, Rozetka, довга робота у треї після sleep/network restore, системний logoff і фактичний автозапуск HKCU користувач має перевірити на development-збірці. Production EXE, production-дані та його автозапуск не змінювалися.
- Підтримку серверних delta-параметрів для всіх API не підтверджено; немає вигаданого `updated_since`. Через це на кожному циклі повторно читається обмежене вікно, що може бути дорожче за справжній delta-запит.
- Для частково недоступного Prom/Rozetka загальний фон показує неповноту й не створює нові ймовірні зв’язки; точний час повтору окремого marketplace-підключення зараз не виводиться окремим рядком трея. App-level cooldown зберігає останній `Retry-After` для джерела маркетплейсів загалом, а не окремий таймер для кожного магазину.
- Важке зіставлення використовує незмінний знімок моделей чеків, але поточний `MarketplaceWorkspaceViewModel.ApplyMatches()` обчислює результат у UI-контексті. На дуже великих вибірках це може викликати коротку затримку інтерфейсу; винесення matcher на worker з перевіркою поколінь залишається окремою роботою.

Джерела контрактів: [Prom public API](https://public-api.docs.prom.ua/), [Checkbox API specification](https://wiki.checkbox.ua/specification/%D0%BA%D0%BE%D0%BF%D1%96%D1%8F_api_specification_%28eng%29.pdf). Для Rozetka застосовано чинний контракт адаптера та його синтетичні тести; публічне джерело для delta-поля не підтверджено.
