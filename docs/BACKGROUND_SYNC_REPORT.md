# Фоновий режим CRMapp — development 1.0.3

## Що зроблено

- Один `BackgroundSyncCoordinator` на процес: перший цикл після старту, далі 1/2/5/10 хвилин (типово 2); таймер і ручний запит зливаються в одну операцію. Відсутня черга пропущених tick. Checkbox і маркетплейси мають окремі результати; збій одного не скасовує інше.
- Робочий діапазон чеків — останні 7 днів за Europe/Kyiv (налаштовується 1–30). Замовлення читаються з відповідним чинним запасом історії для matcher. Це не поточний фільтр календаря. При зміні явно вибраного діапазону поза завантаженими чеками виконується окреме читання; фоновий діапазон залишається тим самим. Режим «Сьогодні» переходить на нову дату після опівночі Києва.
- Список чеків записується як DPAPI-захищений `receipts.dpapi`: обліковий контекст, межі завершеної вибірки, час успіху, схема, метадані й SHA-256 відбитки. Строк зберігання 30 днів, до 30 000 чеків/4 контекстів і обмеження розміру файлу. PNG, PDF, паролі й токени туди не записуються. Дані з кешу показуються перед мережею зі старим часом; при збої Checkbox показано «Дані станом на …; немає з’єднання». `orders.dpapi`, `automatic-matches.dpapi`, `receipt-order-links.dpapi` та історія друку залишилися окремими чинними сховищами.
- Рядки чеків оновлюються за ID; зберігаються їхні об’єкти, вибір у двох вкладках і стан друку. Повна успішна вибірка прибирає лише зниклі рядки в її діапазоні; інші відкриті історичні рядки залишаються. Змінений чек скидає застарілі деталі matcher. Для нових зв’язків повнота Checkbox та увімкнених маркетплейсів обов’язкова. Ручні рішення не переписуються фоновим кешем.
- Трей має відкриття подвійним кліком, меню «Оновити зараз», паузу/відновлення, налаштування й вихід. X приховує вікно, якщо прапорець трея ввімкнено; перше приховування показує коротке пояснення. Явний вихід скасовує worker, звільняє значок; при активному друці просить підтвердження. Параметр `--background` відкриває процес приховано. `--verify-package` обробляється до створення сервісів і worker.
- Один процес на Windows-користувача + канал + корінь даних. Другий EXE передає **лише** фіксований байт локальним named pipe поточного користувача, відкриває чинне вікно та отримує версію. Production і Development мають різні mutex, pipe, кеш і HKCU Run-імена. Автозапуск реєструється тільки через збереження відповідного прапорця; команда — фактичний шлях EXE в лапках + `--background`. Невідповідність шляху показується в налаштуваннях.

## Оновлення старих документів і межі API

Наявні клієнти Checkbox використовують пагінацію `receipts/search` за діапазоном дат; Prom — `orders/list` із UTC-датами й cursor `last_id`; Rozetka — `orders/search` із датами створення. Документований універсальний `updated_since` для цих трьох адаптерів не встановлено, тому worker перечитує **обмежене робоче вікно**, робить upsert за стабільними ID і не просуває стан успішної вибірки після неповної пагінації. Повторна повна сторінка Checkbox і межа 1000 сторінок тепер вважаються неповним результатом, а не успіхом. Відомі пов’язані замовлення поза вікном повторно запитуються за ID; обхід старих записів із лімітом 500 продовжується з локально збереженого курсора, щоб не застрягати на перших 500. Стан, ТТН і фіскальні поля перечитуються через ті ж read-only API. Деталі чеків кешуються чинним matcher; PNG/PDF фон не завантажує.

Після HTTP 429 враховується `Retry-After` Checkbox; коротші внутрішні повтори його не обрізають. Для тимчасових помилок координатор застосовує обмежений backoff, а 401/403 Checkbox призупиняє до явної повторної перевірки налаштувань. Стан кожного підключення Prom/Rozetka вже показується в інформації маркетплейсів; загальний рядок фону показує Checkbox і маркетплейси окремо.

## Перевірки

Локально виконано синтетичні регресії (fake API/printer), включно з керованим часом, злиттям таймера/F5, DPAPI-відновленням іншого контексту, upsert без втрати позначок і стану друку, локальною активацією другого екземпляра та створенням/звільненням tray icon на STA. Весь набір після змін: **241/241** тестів (поточний підсумок перед остаточним пакуванням; повторити після фінального commit). Жоден із цих тестів не виконує фіскальні операції чи фізичний друк.

## Що не перевірено / залишкові обмеження

- Реальні підключення Checkbox, Prom, Rozetka, довга робота у треї після sleep/network restore, системний logoff і фактичний автозапуск HKCU користувач має перевірити на development-збірці. Production EXE, production-дані та його автозапуск не змінювалися.
- Підтримку серверних delta-параметрів для всіх API не підтверджено; немає вигаданого `updated_since`. Через це на кожному циклі повторно читається обмежене вікно, що може бути дорожче за справжній delta-запит.
- Для частково недоступного Prom/Rozetka загальний фон показує неповноту й не створює нові ймовірні зв’язки; точний час повтору окремого marketplace-підключення зараз не виводиться окремим рядком трея. Транспорт Prom/Rozetka дотримується `Retry-After` під час своїх повторів, але після остаточної невдачі app-level backoff не зберігає конкретний server deadline.
- Важке зіставлення використовує незмінний знімок моделей чеків, але поточний `MarketplaceWorkspaceViewModel.ApplyMatches()` обчислює результат у UI-контексті. На дуже великих вибірках це може викликати коротку затримку інтерфейсу; винесення matcher на worker з перевіркою поколінь залишається окремою роботою.

Джерела контрактів: [Prom public API](https://public-api.docs.prom.ua/), [Checkbox API specification](https://wiki.checkbox.ua/specification/%D0%BA%D0%BE%D0%BF%D1%96%D1%8F_api_specification_%28eng%29.pdf). Для Rozetka застосовано чинний контракт адаптера та його синтетичні тести; публічне джерело для delta-поля не підтверджено.
