# Друк усіх накладних і відповідні замовлення — 10.10.2026

Версія 1.0.32 додає вибір, перегляд і підтверджений пакетний друк на вкладці «Усі накладні». Джерелом друку є перевізник, постійний ID його підключення, номер/ID документа та отриманий під цим акаунтом доказ ключа. Замовлення не створюються штучно й не використовуються для вибору ключа доставки; `ShipmentReference.Order` може бути відсутнім у незалежного документа.

НП використовує той самий існуючий маршрут PDF маркування: один bulk-запит для ТТН вибраного акаунта, перевірка PDFium і зіставлення сторінок за їхніми надрукованими номерами. RD використовує існуючі документовані деталі `GET /api/track/{id}` і копію `GET /api/track/label?id=…`. Усі місця та сторінки зберігаються; застосовуються існуючі перевірки фізичного формату, драйвера, межі 100 документів/250 сторінок/80 MiB PNG/256 MiB декодованих растрів. Метадані документа й акаунта перевіряються до запитів; змінений ключ не підміняється іншим підключенням. Докази ключів залишаються в пам’яті, не показуються й не записуються в профіль.

Вибір фіксується у поточному видимому порядку до першого await. Чистий перегляд не викликає backend. Друк потребує підтвердження перегляду, перевірки незмінного набору документів, ключів, налаштувань і геометрії драйвера. Старі рядки після оновлення або зміни періоду не можуть бути передані. Відкладена підготовка скасовується; після початку передавання кнопка скасування не створює враження, що сторінки гарантовано не друкувалися.

Використовується той самий журнал `NotSubmitted → SubmissionUnknown → Submitted` та `LabelPrintCoordinator`. Попередні спроби зіставляються за перевізником, акаунтом і ТТН; налаштовані aliases НП з тим самим ключем враховуються як один акаунт. Невизначене або вже виконане передавання не входить в автоматичний повтор. Успішні галочки знімаються також після оновлення рядків під час передавання; нові або змінені документи не позначаються надрукованими замість старих.

Інформаційна колонка пов’язаних замовлень використовує точний задокументований перевізник + ТТН/ID, додатково перевіряє відомі NP bindings і document Ref. Суми, покупці, дати та фільтр таблиці замовлень не визначають цю відповідність. Кілька реальних замовлень показуються всі; скасовані замовлення з реальним документом залишаються інформацією, не кандидатами автоматичної прив’язки чека. Resolver не записує рішення.

Офлайн-перевірки охоплюють обидва перевізники, багатомісні PDF, помилки/видалення, різні й однакові акаунти, зміну ключа, геометрії чи рядків, підтвердження/скасування, межі пакета, помилки до/після передавання й безпечний повтор. Скомпільований XAML перевіряє галочку, поточну накладну, незалежний перегляд із відсутнім Order, точне замовлення іншої дати, історію та зняття галочки після fake backend. Реальний принтер у тестах не викликається.

Повний набір: 434/434 тестів, exit code 0. Інтерфейс і незалежний двосторінковий перегляд візуально перевірено. Окрема жива перевірка НП отримала одну накладну за 09.10.2026, перевірила її PDF, підготувала одну сторінку без Order та повторно перевірила ключ. Захищений файл налаштувань залишився побайтно незмінним, викликів принтера — 0. Живий RD label-запит не виконувався, бо в локальному профілі немає токена; контракт і поведінку перевірено синтетичними відповідями.
