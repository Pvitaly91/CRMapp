# Перевірка надійності друку

## Семантика статусів

- **NotSubmitted** — операція передавання у spooler ще не починалася. Лише така помилка може бути безпечним повтором, якщо в історії цього чека немає ранішої невизначеної або переданої спроби.
- **SubmissionUnknown** — межу передавання пройдено, але конкретний job ID не отримано. Відсутність job у черзі під час подальшого пошуку не доводить, що чек не друкувався.
- **Submitted** — spooler повернув конкретний `JobIdentifier` або job вдалося відновити за унікальним ім'ям у тій самій черзі.
- **Очікує / Завантаження / Підготовка** — поточний Windows print job ще не створено.
- **Передано Windows** — spooler повернув конкретний `JobIdentifier`. Це не підтвердження виходу паперу.
- **Призупинено / Помилка** з job ID — завдання вже могло частково або повністю надрукуватися; автоматичний повтор заборонено.
- **Результат не підтверджено** — Windows завершила/видалила job, job зник із черги або закінчився період спостереження. Фізичний результат підтверджує користувач.

Програма не очищає чужі черги, не перезапускає Print Spooler і не змінює глобальні налаштування принтера.

## Що виправлено після огляду `0dd9709`

- Історію спроб винесено з рядків таблиці у `%LOCALAPPDATA%\CheckboxBatchPrinter\print-attempts.json`. F5, зміна діапазону дат і перезапуск відновлюють відомий статус та job ID.
- Контекст Checkbox — SHA-256 від нормалізованих API host + login. Сирий login, пароль, JWT, PNG, склад чека та дані покупця в журналі не зберігаються.
- Запис містить attempt ID, receipt ID, принтер, унікальне ім'я job, job ID за наявності, час, стан передавання і останній відомий UI-статус. Строк зберігання — 30 днів, додаткове обмеження — 5000 записів.
- `SubmissionUnknown` синхронно записується перед `PrintQueue.AddJob`. Після винятку виконується короткий best-effort пошук точного унікального імені лише у вибраній черзі; невдалий пошук не перетворює стан на `NotSubmitted`.
- Однакова межа використовується для окремих jobs і спільного job пачки. Невизначений shared job позначає всі чеки, які входили до нього.
- Тестове зображення тепер має незалежні DIP-розміри макета, pixel-розміри та DPI за формулою `pixels = DIP × DPI / 96`. Висота визначається вмістом; додано зовнішню рамку, підписи країв, нижню межу та контрольну QR-зону.

## Автоматичний формат для рулонного драйвера RONGTA

- На встановленому `RONGTA RPP210 Series Printer` WPF PrintTicket не оголошує жодного формату, а запит `50 × 106,7 мм` залишає драйверний формат рулону `48,05 × 2527,49 мм`. GDI того самого драйвера оголошує короткі формати та приймає власну висоту через DEVMODE.
- Коли звичайний WPF PrintTicket не проходить перевірку, програма автоматично створює власний формат тільки для поточного завдання через GDI DEVMODE → PrintTicket. Вона перевіряє прийнятий формат та фактичну область друку до виклику `AddJob` і передає узгоджений ticket на рівні XPS-документа й Windows job. Глобальні налаштування черги не змінюються.
- Логічна ширина драйвера може бути меншою за номінальні 50/58 мм рулону. Програма автоматично вміщує зображення в доступну ширину. Якщо принтер не приймає достатню висоту або область друку, передавання не починається.

## Реальна перевірка

Облікові дані вводяться тільки локально у програмі. Не надсилайте пароль, JWT або ключі в чат чи репозиторій.

1. Відкрити «Налаштування → Checkbox», ввести login/password і натиснути «Перевірити підключення».
2. Завантажити існуючі чеки за сьогодні та переконатися, що список і пагінація відповідають кабінету Checkbox.
3. Відкрити один чек через «Перегляд» і звірити офіційний PNG.
4. Обрати один чек, надрукувати, звірити job ID у програмі та фізичний чек.
5. Відсортувати таблицю у потрібному порядку, обрати три різні чеки та звірити порядок фізичних чеків.
6. Для короткого й довгого чека перевірити весь текст, QR-код, відсутність обрізання та автообрізання, якщо різак увімкнено у драйвері.

## Перевірки, що потребують фізичного принтера

- Реальний Checkbox login, отримання приватних чеків та фізичний друк: **не виконано**, очікує локального підтвердження користувача.
- Реакцію RPP210 на власну висоту та повідомлену imageable area перевірено в пам’яті; фізичний результат друку потребує підтвердження користувача.
- Відновлення job після реального винятку `AddJob` і звірка його у Windows queue: **не виконано**; для безпеки відсутність знайденого job лишається невизначеним результатом.
- Автообрізання: **не виконано**, залежить від обладнання та налаштувань драйвера.

## Відомі обмеження

- Windows spooler не дає універсального доказу, що папір фізично вийшов і був відрізаний.
- Драйвери, для яких ні звичайний PrintTicket, ні формат через GDI не дають придатну сторінку та imageable area, блокуються до передавання job.
- Спостереження за job триває обмежений час; після нього результат залишається непідтвердженим.
- У режимі одного job для пачки всі сторінки використовують висоту найдовшого чека; типовим і рекомендованим залишається окремий job для кожного чека.
