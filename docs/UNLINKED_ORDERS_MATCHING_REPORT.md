# Пошук лише серед замовлень без зв’язку — 03.10.2026

Версія 1.0.21 змінює попереднє правило повторного перерахунку всіх ймовірних пар. Уже знайдені автозв’язки виключають свої замовлення і чеки з нового товарного графа. Повторний продаж того самого товару за тією самою ціною більше не робить раніше пов’язане замовлення конкурентом для нового чека.

## Поведінка

- Ручні, точні фіскальні та збережені автоматичні зв’язки резервують замовлення. Пов’язані чеки не порівнюються повторно з новими замовленнями; деталі їхніх товарів не запитуються повторно.
- Ймовірні пари зберігаються окремими ключами й відбитками документів у наявному зашифрованому `automatic-matches.dpapi`. Ручні рішення не створюються. Старий кеш v8 переносить збережені пари один раз; новий граф має версію v9.
- Збережена пара резервує замовлення і тоді, коли її чек поза поточним діапазоном. Межа — 5000 пар на обліковий контекст, строк — налаштований TTL кешу, без продовження дати створення при простому повторному показі.
- Ручне відв’язування, відхилення, зміна ручної пари та точні фіскальні дані мають пріоритет. Зміна власного відбитка чека або ключових полів його замовлення прибирає застарілий автозв’язок. Поява стороннього конкурента не скидає пару.
- Часткове оновлення зберігає старі пари, але не створює нові до повного завантаження джерел. Початковий показ за сумою під час завантаження товарів не записується як готовий зв’язок до завершення запиту.
- Дві однакові вільні пари лишаються неоднозначними. Не застосовується довільний розподіл за часом, номером чи порядком API.

## Перевірки

До зміни production-коду нові регресії відтворили проблему: 351/355 тестів; чотири падіння — повторний продаж, замовлення з чеком поза діапазоном, нові конкуренти та перенесення старого кешу.

Після зміни: 356/356 тестів, exit code 0. Нові сценарії перевіряють два однакові продажі вранці й увечері після серіалізації кешу, виключення вже пов’язаних замовлень зі списку кандидатів, відсутність повторних запитів товарів, ручні/фіскальні пріоритети, змінені документи та перенесення v8. Windows/STA перевірка проходить через справжні ViewModel і обидві таблиці. Збережено перевірки невизначених нових пар, повернень, друку, вибору, фонової синхронізації та ізоляції облікових записів.

Збирання успішне. У середовищі залишаються наявне попередження WFAC010 для DPI manifest і NU1900 через недоступне джерело аудиту NuGet; помилок компіляції немає. Тести використовують синтетичні API та принтер; фізичний друк не виконується.

Додатковий локальний аудит виконав нове зіставлення лише на копії реального кешу в пам’яті, без API-запитів чи запису профілю. Перенесено 153 наявні пари. Старі snapshot-и вже не містять призначених пар для чеків 4581, 4583, 4587 і 4598: попередній алгоритм утратив їх до цього виправлення. Такі вже втрачені пари не відновлюються довільним вибором; нова версія зберігає наявні й наступні знайдені зв’язки. Для вже нерозподіленої групи потрібне разове ручне рішення.
