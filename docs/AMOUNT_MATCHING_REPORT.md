# Зіставлення за сумою й товарами — 26.09.2026

## База та межі

Віддалена development-гілка перед роботою: `codex/checkbox-marketplace-orders`, `d9d92f798cc0050e2202b3481607e2b33ab434ec`.
Актуальний чистий локальний код уже мав новіші зміни: `128000e4fdb96c99dbafc7d3cd04e359cbffea15`.
Development-гілку fast-forward оновлено до нього: production-пакування, кнопки вибору, скидання позначок після друку та «Чеки за сьогодні» збережені.

Змінено локальний matcher, метадані для безпечного порівняння, відображення та тести. Не змінено parser сум Prom, `self_receipts=true`, офіційний PNG, STA/GDI-друк, пакет/історію друку, API-маршрути або профілі пакування. Нові поля метаданих сумісні зі старим кешем; автоматичної міграції файлів немає.

## Правила

1. Ручне підтвердження має пріоритет, потім перевірений фіскальний зв’язок. UUID / fiscal_code не виводяться із суми. Збережено точний ланцюжок `related_receipt_id` для повернення.
2. Для завершених звичайних продажів будується один двосторонній граф для всіх релевантних завантажених документів. Видимість рядків, пошук, сортування та фільтри не змінюють граф.
3. Точна нормалізована сума `decimal` — основний критерій. Призначення відбувається лише за єдиним кандидатом в обох напрямках, без фіскальної/ручної зайнятості чи відомої суперечності. Нуль, невідома сума та інша валюта не підміняються; різниця 0,01 не допускається. Невідома валюта — явне обмеження.
4. Без повного кошика, SKU або ціни позиції взаємно унікальна сума дає **«Автозв’язок: унікальна сума»**. Це ймовірна пара без обов’язкового ручного підтвердження, не фіскальне підтвердження.
5. Товарна перевірка має чотири окремі стани: збіг, суперечність, недостатньо даних, завантаження. Повні нормалізовані назви та сумарні відомі кількості дають **«Автозв’язок: сума й товари»**. Ціни позицій між системами не повинні бути повністю однаковими. Розбиття однакових позицій на рядки не змінює порівняння. SKU без спільного простору артикулів не є ключем.
6. Обережна нормалізація: регістр, Unicode-пробіли, типографічні тире/лапки. Модельні цифри, напруга, колір, розмір, роз’єм не стираються. Скорочення/запис іншою мовою можуть залишитися недостатніми даними; нечіткого доказу однакового товару немає.
7. Відомі відмінності повних товарних даних блокують призначення. Для A/X і B/Y з однаковою сумою та чеків X/Y граф розділяється на правильні пари. Для двох однакових замовлень різних покупців і одного/двох однакових чеків залишається неоднозначність. Відсутні деталі конкурента не прибирають його з графа.
8. Немає послідовного виключення ймовірних пар, підбору за ближчим часом, ID, порядком API або розміром групи. Підтверджена історія враховується навіть поза поточним списком. Відхилення одного кандидата не доводить інший. Це не глобальне 1:1 для ручних/точних продажів і повернень.
9. Область: календар чеків плюс налаштований запас історії замовлень, включно з розширенням. Замовлення не пізніше чека; немає жорсткої межі 30 днів у workspace. Повний діапазон видно в поясненні. Кешовані замовлення поза ним лишаються в таблиці, але не створюють евристичних пар.
10. Незавершена пагінація, збій синхронізації або скасування — **«Перевірка неповна»**, без нових призначень. На початку нового sync стара ймовірна унікальність знімається до перевірки. Поява конкурента перетворює непідтверджену пару на неоднозначну; ручне рішення зберігається.
11. Суми не коригуються під бажану пару. Prom використовує наявний нормалізований `price`; Rozetka — чинний пріоритет `cost_with_discount / cost / amount`. Окрема доставка дозволена лише коли відомий повний склад позицій підтверджує `Total = сума товарів`; нічого не додається/віднімається. Без такого доказу лишається кандидат із поясненням. Відомі знижки, передоплата/часткова оплата, повернення в позиціях, округлення й суперечлива арифметика також потребують перевірки.
12. Ймовірні зв’язки не записуються у файл ручних рішень. Вони відновлюються перерахунком зі snapshot; у пам’яті окремо зберігаються підстава, товарний стан та область. Підтверджений пакет друку не змінюється.

## Інтерфейс

- Назви: «Автоматично зіставляти за сумою й товарами» та «Зіставити за сумою й товарами».
- В обох таблицях є підстава зв’язку та відповідний номер документа. Номер замовлення/«Кандидати» відкриває локальний блок деталей, кнопка у «Відкрити чек» передає конкретний чек до наявного preview.
- Розрізняються ручний, точний, ймовірний зв’язки, неоднозначність, суперечність товарів, недостатні дані й неповна перевірка. Точна підстава UUID/URL/номер збережена в поясненні.
- Для неоднозначної групи в розгорнутому блоці: кількість замовлень/чеків, покупці замовлень, товари, дати/час та швидка ручна дія «Прив’язати вибрані». Покупець не вигадується для Checkbox.
- Фільтр «Є чек» враховує також ймовірні пари; «Ймовірний зв’язок» виділяє їх окремо. Фільтри не впливають на обчислення.
- Довгі повідомлення залишилися у підказках і згорнутому блоці, таблиці лишаються поруч, панель кнопок — одним рядком.

## Перевірка на локальних даних

Виконано лише read-only аудит наявних зашифрованих кешів. Порівняння тотожності Prom-підключень використовує наявну логіку токенів тільки в пам’яті; секрети, їхні відбитки, payload, номери замовлень і персональні дані не виводилися та не потрапляють у Git.

| --- | ---: | ---: |
| Унікальні активні замовлення Prom | 1293 | 741 |
| Замовлення Rozetka | 0 | 0 |
| Відома позитивна сума/UAH | 1293 | 741 |
| Групи сум з одним замовленням | 157 | 127 |
| Групи однакових сум з кількома замовленнями | 128 | 86 |
| Замовлення у повторюваних групах | 1136 | 614 |
| Записи з окремою доставкою/знижкою | 1216 | 691 |

Ці агрегати — **не результат прив’язки до реальних чеків** і не кількість неоднозначних пар у вибраному календарі. Локальний кеш замовлень не містить актуального набору Checkbox-чеків; записи чеків із сум замовлень не вигадувалися. Live API цього етапу не викликалися. Rozetka перевірена синтетичними адаптерними/фіскальними сценаріями, не реальним акаунтом.

SHA-256 усіх прочитаних файлів інтеграцій до/після аудиту незмінні в обох профілях. Production EXE 1.0.1 не замінений: SHA-256 `9E7F1C6675BBF6409092B6FBD817D400908B2C907E7EA676AE47F435D69B0F80`.

Для реального приймання потрібно відкрити окремий development-білд, завантажити чеки потрібного касира/періоду та замовлення. Однакові суми/товари різних покупців без додаткового доказу, фіскальні конфлікти, нерозібрана семантика оплати й неповні вибірки залишаються для ручного рішення. Фізичний друк не потрібний для перевірки цього алгоритму й цього етапу не виконувався.
