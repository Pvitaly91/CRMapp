# Групи по три чеки та растрові сторінки — 1.0.81

## Запит і спостереження

Користувач попросив групувати по 3 чеки на одне завдання та надав фото зайвих символів між чеками після переходу 1.0.80 на окремі завдання.

Перевірка локального профілю й драйвера 22.10.2026 виконана лише для читання. Останній спільний друк о 18:43 містив 3 різні чеки, кожен переданий один раз. У переглянутих оригінальних PNG із цього пакета зайвого тексту немає. У RPP210A USB не налаштовано SeparatorPageFile; використовується RPP210 / winprint / RAW, роздільність 203 × 203 DPI. Глобальні налаштування принтера не змінювалися.

Раніше PNG чека передавався як зображення, а доданий заголовок замовлення/ТТН — як векторний текст WPF. Для старого драйвера WPF перетворює [XPS на GDI](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/documents/printing-overview). Саме шлях тексту/шрифтів є ймовірним джерелом артефактів. Фото та журнали не доводять конкретну помилку прошивки або драйвера; виправлення прибирає окреме передавання тексту/шрифтів. Фізичний результат потребує перевірки під час звичайного друку користувача.

## Поведінка

Усі три маршрути друку чеків використовують спільний ліміт 3 чеки на завдання: спільний друк із наклейками, чеки позначених замовлень і вибрані чеки. Послідовність із 7 чеків передається як 3 + 3 + 1, із 8 — 3 + 3 + 2. Порядок фіксується з вибраної таблиці до очікувань і підтвердження; фільтри й сортування під час друку його не змінюють.

Всі групи проходять перевірку зображень, довжини та можливостей драйвера до першого передавання. Група може мати кілька обмежених довжиною сторінок, але все одно одне завдання Windows. Надто довгий одиночний чек блокує підготовку всього пакета.

Готова сторінка із заголовками, зображеннями та розділювачами раструється в роздільності, підтвердженій драйвером. Передаваний XPS містить лише зображення без векторних Glyphs і вбудованих шрифтів. Розміри сторінок, заголовки, порядок і одна копія зберігаються. Пам'ять для растру обмежена; невідома роздільність або завеликий растр зупиняють підготовку.

Після успішного передавання всі чеки групи записуються в історію до наступної групи. Після невизначеної помилки вся поточна група позначається як потенційно передана, наступні групи залишаються не переданими. Прийнята попередня група не надсилається повторно автоматично. Помилки історії або журналу також не запускають повтор друку. Повтор перерваного завдання самим драйвером може охопити до 3 чеків.

## Перевірки

Development: 776/776 тестів. Окремо пройшла перевірка скомпільованих WPF-вікон і прив'язок. Сценарії всіх трьох маршрутів перевіряють 3+3+1 і 3+3+2, збереження групи до передавання наступної, невизначений результат другої групи без повтору першої, непереданий залишок, збереження порядку та помилки підготовки/історії/журналу.

Після запису XPS перевірено відсутність Glyphs та ресурсів шрифтів і точну відповідність усіх пікселів вбудованого PNG підготовленому растру. Додатково перевірено нижній край при 203/300 DPI, дробові розміри сторінок, кілька сторінок у межах одного завдання й відмову до надмірного виділення пам'яті. Команда `--receipt-raster-smoke` запускає ці п'ять перевірок окремо. Під час їх розробки усунуто помилку тестового читання ресурсу ZIP: перед декодуванням він копіюється у потік із позиціюванням, щоб WPF не повертав тимчасовий кадр 1×1 замість завершеного PNG. Це не було пошкодженням виробничого XPS; додаткового перекодування у виробничому шляху немає.

Діагностика `--receipt-driver-smoke "RPP210A USB"` підготувала 20 синтетичних чеків як 7 завдань: шість груп по 3 й остання з 2. Підтверджено 203×203 DPI, одна копія, повністю растрові сторінки; висота груп 271,364 мм, останньої — 180,676 мм. Растровий перегляд першої групи перевірено візуально: три послідовні заголовки й повний останній чек. Завдання друку не створювалися. Фізичний друк і API-запити для перевірки не запускалися.
